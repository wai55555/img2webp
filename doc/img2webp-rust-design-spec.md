### 1.2 変換パイプライン（`main()` → `plan_jobs()` → `run_job()` → `convert_image()`）

1. `load_config(PROJECT_DIR / "config.ini")`。`PROJECT_DIR` はスクリプトのあるフォルダで、相対パスは作業フォルダではなくここ基準で解決する。
2. Pillow の WebP 対応を確認（`features.check("webp")`）し、入力／出力フォルダを自動作成する。
3. 出力フォルダの `.img2webp.sqlite3` を開き初期化する（WAL、`synchronous=NORMAL`、`user_version` 0/1 のみ許可。接続時の busy timeout は Python の `sqlite3.connect` 既定で 5秒）。
4. `plan_jobs()`: 入力以下を `rglob("*")` で再帰走査し、シンボリックリンクを除外、全ファイル分の宛先を**処理前に**一括決定する（衝突命名は §1.4）。
5. 逐次ループ: 再利用判定（DB 記録と一致すれば SKIP）→ adopt 判定 → `run_job()`。
   - `run_job()`: 宛先と同フォルダに `tempfile.mkstemp` で一時ファイルを作り、そこへ変換／コピーし、日時を付け、処理中に入力が変わっていないか再 stat で確認してから `os.replace` で原子的に置く。失敗時は既存出力を残す。
   - 成功記録は `db_commit_every` 件ごとにまとめて commit。通常終了・中断時は残りも commit する。
6. 終了コード: 0＝全成功、1＝失敗ファイルあり、2＝設定／DB エラー、130＝中断。
7. 出力メッセージは `CONVERT` / `COPY` / `SKIP` / `ADOPT` / `WARN`（stderr）/ `ERROR`（stderr）と、最後の「完了: 変換 N / コピー N / 再利用 N / 登録 N / 失敗 N」行。すべて日本語で形式が固定されている。なお完了行の「再利用」には、分類スキップ・DB 一致による再利用・上書き無効によるスキップの3種が合算される（`counts["skipped"]` をそのまま表示するため）。
8. 変換時の検証: 拡張子と実際の形式の不一致は変換失敗（`convert_image()` 冒頭で判定。判定は Pillow の形式名（`image.format`）と拡張子から期待される形式との比較による。MPO は JPEG と別形式として失敗する）。フレームごとの duration の型・範囲（数値でない／負は失敗）と、複数フレーム時の loop の型・範囲（int でない／負は失敗）も検証する。保存できるフレームが0なら失敗し、`default_image` のみの APNG はこの経路で失敗する（開始フレームが1で巡回範囲が空になるため）。
9. DB エラーはファイル単位の失敗にならない: 逐次ループ内の `sqlite3.DatabaseError` は再 raise され、バッチ全体を打ち切って終了コード 2（「処理履歴DBエラー: …」）になる。ファイル単位の失敗として数えられるのは DB 以外の例外だけである。
10. 中断メッセージは2種ある: 初期化段階は「中断しました。」、逐次ループ中は「中断しました。記録済みのファイルは次回再利用されます。」。

### 1.3 設定（`config.ini`、全項目必須・未知キー／未知セクションはエラー）

| セクション.キー | 現行値（同梱 config.ini） | 意味 |
| --- | --- | --- |
| `paths.input_dir` / `paths.output_dir` | `inputs` / `outputs` | 同一・親子関係は禁止。パスは `Path.resolve()` で解決してから比較する（resolve は非 strict で、存在しないパスでも例外にならず、存在する祖先までを解決して残りを繋ぐ。初回実行では output_dir が存在しない状態で解決されるのが通常経路）。Windows ではパスの同一・親子の比較は大小文字を区別しない等価で行われる（Rust 版では resolve 後のパス文字列を小文字化して比較する。現行の normcase 相当であり、Unicode の casefold とは異なる。親子判定はパス要素単位で行い、文字列の前方一致では行わない） |
| `webp.quality` | 90 | 0〜100。WebP 品質はこの1項目のみ（§2 SPEC-01） |
| `animation.missing_duration_ms` | 80 | フレーム表示時間がない場合の補完値。正の整数 |
| `copy.jpeg` | true | true＝JPEG をそのままコピー、false＝WebP 変換 |
| `copy.avif` / `copy.webp` | true | true＝バイト列コピー、false＝スキップ（変換はしない） |
| `copy.other_files` | true | 対象外形式（WebM 等）もコピーするか |
| `output.overwrite_existing` | true | 履歴と一致しない既存出力を更新してよいか |
| `output.reuse_unchanged` | true | DB 記録と一致する出力を再利用するか |
| `output.adopt_untracked` | false | 履歴のない既存出力を検査なしで登録するか |
| `output.db_commit_every` | 32 | SQLite commit のまとめ件数（正の整数で検証される） |
| `preserve.metadata` | true | 変換時に Exif・XMP・ICC・生成情報を引き継ぐか |
| `preserve.timestamps` | true | 元ファイルの日時を引き継ぐか |

CLI 引数は存在しない。設定ファイルの場所も固定（スクリプト隣の `config.ini` のみ）。

検証は `configparser` の意味論に依存する部分が大きい: キー名は大文字小文字を区別しない（パーサが小文字化する）、真偽値は `getboolean` の受理集合（`1`／`yes`／`true`／`on` 等も可）、整数は Python の `int()` 構文（符号や前後の空白を許す）、重複キー／重複セクションは strict エラー、`[DEFAULT]` セクションにキーが1つでもあるとエラーになる（空の `[DEFAULT]` は通る）。行頭（インデント可）の #／; で始まる行はコメントとして読み飛ばされ、複数行値の途中でも継続状態に影響しない。セクション見出しは行頭から行内の最後の ] までで判定され、] の後の文字列は無視され、セクション名の空白は前後も含めて保持される。セクション名は大文字小文字を区別する（小文字化されるのはキーだけである）。Rust 側で INI を自前実装する場合はこれらの受理範囲まで再現しないと互換が崩れる（決定点 D-INI）。また `paths` の検証は非対称で、input_dir には「ファイルが指定されている」チェックがあるが output_dir には無い。

### 1.4 分類と出力命名（`classify()` / `plan_jobs()`）

- `.png` / `.gif` は常時変換。`.jpg` / `.jpeg` は `copy.jpeg` で分岐。`.avif` / `.webp` はコピーかスキップのみ（変換しない）。その他は `copy.other_files` で分岐。分類は拡張子（`Path.suffix` 相当）で行うため、ファイル名自体が拡張子だけの名前（`.png` 等）は接尾辞が空になり「その他」の分岐に落ちる。末尾ドット形（`file.` 等）も接尾辞なしとして扱われる。
- 変換先は原則 `<名前>.webp`。割当はコピー側を先に処理し（宛先キー順）、コピー側が名前を優先する。同じ宛先に複数が対応する場合だけ変換側が `<名前><元拡張子>.webp` になるが、元拡張子は小文字化される（`sample.PNG` → `sample.png.webp`）。それでも衝突すれば連番を付け、挿入位置は stem の末尾である（`sample.png-2.webp` の形で、`sample-2.png.webp` にはならない）。衝突判定は `casefold` した POSIX 相対パスで行う（大文字小文字違いも衝突扱い）。実行順（ジョブの処理順）は入力相対パスの casefold 順。なお拡張子の小文字化（`.lower()`）は分類・シグネチャ・形式判定など複数箇所で別々に行われており、SPEC-02 の `casefold` とは別の互換要素である。
- 状態 DB のファイル名（`.img2webp.sqlite3` と `-wal`／`-shm`／`-journal` の計4種）は宛先として予約済みだが、帰結は除外ではなく連番リネームである。予約が効くのは入力ルート直下の同名ファイルのみ（予約集合はディレクトリ無しのファイル名で、宛先キーである相対パスと一致するのがルート直下だけのため）。サブフォルダ内の同名ファイルには効かない。

### 1.5 状態 DB（再利用判定）

- テーブル `completed_jobs`: 入力の相対パスを主キーに、宛先、入力のサイズ／mtime／ctime、出力のサイズ／mtime、設定シグネチャ（JSON）を記録。
- シグネチャ（`settings_signature()`）: `pipeline`（`PIPELINE_VERSION = 2`）、`platform`（`os.name`、値は `nt`／`posix`）、`action`、timestamps 設定、変換時は quality／metadata、さらに拡張子が `.png`／`.gif` の変換ジョブではアニメーションかどうかを問わず `missing_duration_ms`。JSON はキーソート＋区切りなし（`separators=(",", ":")`）で文字列化され、記録との完全一致で再利用が判定される。
- ハッシュは計算しない（README 明記）。同じサイズ・日時での内容書き換えは検出できない、が現行仕様。
- 初期化（`initialize_state()`）は `user_version` の確認とテーブル作成（IF NOT EXISTS）のみで、既存テーブルのスキーマ自体の検証はしない。

### 1.6 メタデータ引き継ぎ（`prepare_metadata()` / `source_text()` / `verify_metadata()`）

- Exif は piexif で読み、辞書として保持。Orientation は変換対象の値（2〜8）の場合に画素側へ反映し、出力 Exif から除去する（値 1 や範囲外の値はそのまま残る）。Orientation の取得元は piexif の辞書（0th IFD）が第一で、辞書に無い場合は Pillow の `image.getexif()` へフォールバックする。
- 生成テキスト: PNG の `parameters` を先頭に、その他の PNG テキスト（XMP キーを除く）を `キー: 値` 行で連結。JPEG／GIF はコメント。既存 `UserComment` が空ならそれに入れ、値があれば `XPComment`（UTF-16LE）へ回す。ただし XPComment 側の判定は「値があるか」ではなくタグの存在自体であり、空の XPComment があるだけで変換失敗になる。生成テキストの連結規則（`source_text()`）: PNG は `parameters` を先頭に、残りのテキストを info の辞書挿入順（重複キーを除きチャンク順）に連結する。値が文字列でないエントリは黙って捨てられ、空文字列の値も落とされる。info に同名キーが複数ある場合は最後の値が勝ち、連結位置は最初の出現位置になる（辞書の意味論）。XMP キーの除外判定は大文字小文字を区別しない（`parameters` の判定は完全一致）。JPEG／GIF のコメント等、bytes の値は UTF-8 で復号し、失敗したら latin-1 で復号する。PNG のテキストチャンクの復号は種別で決まり、tEXt／zTXt は latin-1、iTXt は UTF-8 である。
- Stealth PNG Info（§1.7）を抽出し、テキストがあれば生成テキストへ連結する。
- ICC プロファイルと XMP を引き継ぐ。ただし ICC は経路で扱いが分かれる: RGB 系はそのまま引き継ぐが、CMYK／L／LA で ICC がある場合は LittleCMS（Pillow の `ImageCms`）で sRGB へ変換し、引き継がれるのは元の ICC ではなく生成した sRGB プロファイルになる。色空間と ICC の不一致は変換失敗にする。保存後検証の ICC 比較も変換後のプロファイルに対して行われる。色正規化（`normalize_color()`）の分岐は細かい: RGB／RGBA でも ICC の色空間が RGB でなければ失敗する。CMYK で ICC が無ければ単純な RGB 変換で ICC は付かない。LA は L チャンネルだけを変換して alpha を後付けする。L（ICC 無し）や P 等、上記に挙がらないモードは末尾の汎用変換に落ち、alpha の有無で RGB／RGBA へ変換される（ICC がある場合は色空間が RGB でなければ失敗）。`output_icc` はフレームごとに上書きされ、最終フレームの値が出力全体の ICC になる。
- `preserve.metadata` の真偽で失敗の意味論が変わる: Exif の解析に失敗した場合、`true` では変換失敗、`false` では握り潰して空の Exif で続行する。ただし失敗の意味論の非対称は Exif 解析だけではない: Exif データの型エラー（真値で bytes でない場合）は真偽によらず常時失敗し（falsy な非 bytes 値は Exif 無しとして進む）、ICC の型エラーも `convert_image()` 側の別チェックで常時失敗する。ICC の解析失敗（bytes だが解析できない場合）も真偽によらず変換失敗になる。XMP の型エラーは `true` の経路でのみ失敗し、`false` では無視される。Orientation の画素反映は `false` でも常に行われる（出力に Exif 自体は付かない）。PNG のメタデータの実効取得範囲は対象ごとに異なる（Pillow が開く過程で収集される範囲が効くため）。実測済みの範囲: 生成テキスト・Exif 辞書・ICC・XMP は IDAT 前方のみが対象で、Orientation のフォールバック（`getexif()`）は IDAT 後方の eXIf も対象になる（Pillow 10.2.0 での実測。ここでいう ICC は Pillow が返すプロファイルであり、iCCP チャンク自体の後方配置の扱いは未実測の側に含まれる）。これ以外の対象（iCCP チャンク自体の配置を含む）の具体的な範囲は未実測であり、Phase 0 で IDAT 後方にテキストチャンク／eXIf／iCCP を持つフィクスチャを使って対象ごとに実測し、本節へ記録する。
- 保存後に `verify_metadata()` で出力を開き直し、UserComment／XPComment の一致を必須確認（不一致は失敗）、他の IFD（0th／Exif／GPS／Interop／1st の5種）・サムネイル・ICC・XMP の差異は警告にする。ただし検証の期待値は、読み込み時の辞書化と dump→load 往復を経た後の値で作られるため、その過程で落ちたタグは期待値側にも無く、検証では検出できない（BUG-13）。

### 1.7 Stealth PNG Info（`stealth_text()` / `png_16bit_pixels()`）

- 列優先（column-major）の LSB 走査。対象は alpha チャンネル（`stealth_png`）と RGB（`stealth_rgb`）、接頭辞 `info`（無圧縮）と `comp`（zlib/gzip、`zlib.decompressobj(47)`）。
- ワイヤ形式: 接頭辞は15バイト（`stealth_png`／`stealth_rgb` ＋ `info`／`comp`）、続く4バイトが big-endian のビット長で、8の倍数でなければならない。16bit のサンプルは各サンプルの下位バイトを取る。モードの試行順と失敗時の意味論は 8bit と 16bit で非対称である（16bit は、ヘッダと長さの検証を通過した後の全量デコードに失敗すると、その時点で空文字を返して終了し、次のモードを試さない）。PNG チャンクの CRC は検証しない。
- 制限: 各辺 16,384px、画素データ約 512MiB、Stealth 情報は展開前後とも 8MiB。なお 512MiB の上限値（`MAX_PNG_BYTES`）は3つの異なる量に共用されている: 16bit の展開後サイズ、IDAT の累積サイズ、8bit の幅×高さ×バンド数。
- 8bit: Pillow の画素（`image.load()` 後）に直接アクセスして先頭 152bit のヘッダだけ読み、一致した場合のみ Pillow の転置・チャンネル抽出で一括復号する。対象モードは RGB／RGBA／LA のみで、L／P／I 等では黙って空文字を返す。
- 16bit: Pillow にはグレースケール用の I;16 モード等はあるが、16bit RGB 等は読み込み時に 8bit 化されるため、自前の PNG デコーダ（`png_16bit_pixels()`）を持つ。非インターレース、色タイプ 2/4/6 のみ。IDAT 全体を zlib 展開し、ヘッダ判定時は必要範囲だけフィルタ復元する。ペイロードがある場合は全量を再デコードする。
- APNG では Stealth は開いた直後のフレーム（既定画像を含む先頭フレーム）の画素から読まれる（フレーム巡回の前）。

### 1.8 アニメーション（`convert_image()` のフレームループ）

- APNG／GIF は `image.seek()` で全フレームを巡回し、`image.copy()` → 向き適用 → 色正規化したフレームを**全てメモリ上のリストに保持**してから Pillow の `save_all` でアニメーション WebP として保存する。
- APNG で `default_image` がある場合は先頭フレーム（既定画像）を除外する。
- duration はフレームごとに取得し、無い場合は `missing_duration_ms`。`round()` で整数化。loop は入力値を引き継ぎ、無い場合は GIF＝1、他＝0。
- 保存オプションは `quality` のみ。Pillow の WebP 保存の既定では method は静止画 4／シーケンス 0、lossless は指定なし＝常時 lossy（裏取り: Pillow 公式ドキュメントの WebP 節）。

### 1.9 テストとプラットフォーム

- テストは unittest 2ファイル。機能カバレッジは広いが、性能テスト、最適化 GIF（部分フレーム／disposal）のフィクスチャ、16bit PNG の**画素**忠実度テストは無い（16bit は Stealth 抽出のみテストされている）。現行テストの約1/3は white-box（内部関数の mock、定数のパッチ、`sys.modules` への注入等）で、Rust 側にそのままの対応面が無い。「現行テスト相当」の内訳は §6 の Phase 0／1 で振り分ける。
- Windows が主対象（`.bat`、pywin32 で作成日時を引き継ぎ）。POSIX では作成日時は対象外。

### 2.1 正しさ（BUG）

#### BUG-01 最適化 GIF の部分フレーム／disposal の見た目が崩れる可能性 ― 要実測
- 場所: `convert_image()` のフレームループ（`image.seek(index)` → `image.copy()`）。
- 条件: 差分フレームや disposal 指定を持つ最適化 GIF。テストは全面フレームの単純な GIF のみで、この経路のフィクスチャが無い。
- 見立て: 頻度 不明（要実測 ― 本ツールの入力母集団で最適化 GIF の割合は未確認。§4.2 の標本調査で確認する）／重大度 高（崩れれば出力アニメーションが別物になる）。
- 備考: Rust 側にも関連する差異がある。`gif` クレート単体は raw フレームしか返さないが、`image` 0.25 の `GifDecoder` は disposal 合成済みのフレームを返す（2026-11-27 に docs.rs で再確認）。ただし Disposal=Background の消去は透明黒で行われ、背景色が不透明な GIF では Pillow（背景色で埋める）と後続フレームの画素がずれうる。これが Rust 側の新しい差異候補であり、BUG-01 フィクスチャに含める。

#### BUG-02 `quality = 100` でも lossless にならない
- 場所: `convert_image()` の `save_options`（`quality` のみ指定）。
- 条件: 常時。Pillow の WebP 保存では lossless は独立したフラグで、quality 100 は「最も高品質な lossy」にすぎない（Pillow 公式ドキュメントで裏取り）。
- 見立て: 頻度 高（設定すれば効くと思いがち）／重大度 中（画素の完全保存を期待する用途では欠落。ただし現行 `doc/plan.md` の仕様自体が quality のみなので、バグというより仕様の制限。Rust 化では §7 項目1 の決定（設定項目として追加）で扱う）。

#### BUG-03 再利用シグネチャにエンコーダ／ライブラリの版が入っていない
- 場所: `settings_signature()`。
- 条件: Pillow／libwebp／piexif をアップグレードしても、`PIPELINE_VERSION` を手で上げない限り既存の出力がそのまま再利用される。エンコーダの出力（画質・サイズ）は版で変わりうる。
- 見立て: 頻度 中（依存更新のたび）／重大度 中（「再利用＝同じ設定で作り直した結果と同じ」という前提が静かに崩れる）。

#### BUG-04 一時ファイルのパーミッションが 0600 のまま出力になる
- 場所: `run_job()` の `tempfile.mkstemp` → `os.replace`。mkstemp は 0600 で作り、その後の chmod が無い。
- 条件: POSIX では全出力。Windows では ACL の扱いが異なるため要実測。
- 見立て: 頻度はプラットフォーム別 ― 主対象の Windows では低（0600 の意味論がそのまま適用されない。要実測）／POSIX 運用では高（全出力に影響）／重大度 低〜中（他ユーザ／他プロセスから読めない出力になる。通常の umask 既定より厳しい）。

#### BUG-05 `overwrite_existing = false` の存在チェックと置換の間の競合（TOCTOU）
- 場所: `run_job()` 冒頭の `destination.exists()` 確認と末尾の `os.replace`。
- 条件: チェック後に別プロセスが同名ファイルを作ると、無条件の `os.replace` で上書きしてしまう。
- 見立て: 頻度 低（単独運用が前提のツールのため）／重大度 中。

#### BUG-06 Windows の作成日時が最終ファイルに残るか実機未検証（不具合の可能性は低い）
- 場所: `set_windows_creation_time()` の呼び出し位置（置換前の一時ファイルに対して実施）。
- 条件: Windows のみ。一時ファイルは宛先と同一フォルダにあり、`os.replace` は同一ボリューム内のリネーム相当のため、作成日時は保持される可能性が高い。未確認なのは事実確認そのもので、テストは API 呼び出しの引数しか検証していない。Phase 0 で実ファイルの作成日時を確認するフィクスチャを必須とする。
- 見立て: 頻度 ―（不具合かどうか自体が未確定）／重大度 低。

#### BUG-07 Stealth の辺制限（16,384）と WebP の寸法上限（16,383）の不一致
- 場所: `stealth_text()` の制限値と、WebP エンコード上限。
- 条件: 一辺 16,384px の画像は Stealth 走査を通るが、WebP の上限は 16383×16383（libwebp の制限として裏取り済み）でエンコードは必ず失敗する。走査とデコードのコストを払った後に失敗する。
- 見立て: 頻度 低／重大度 低（無駄な処理と分かりにくい失敗理由）。

#### BUG-08 メモリ不足が「ファイル単位の失敗」として処理され続ける
- 場所: `main()` の per-job `except Exception`（`MemoryError` もここで捕まる）。
- 条件: 巨大画像でメモリ不足になると、その後も次の巨大画像で同じことを繰り返し、最悪はプロセス全体が落ちる。
- 見立て: 頻度 低／重大度 中。入力の画素数上限も Pillow 既定の decompression bomb 閾値任せで、コード側に明示が無い。

#### BUG-09 設定エラーの詳細が不足分しか出ない
- 場所: `load_config()` のセクション検証（missing と unknown の両方がある場合、unknown が表示されない）。
- 見立て: 頻度 低／重大度 低（設定ミス修正が1往復増えるだけ）。

#### BUG-10 16bit PNG の画素忠実度が未検証 ― 要実測
- 場所: `convert_image()`（Pillow 経由の読み込み）と Stealth 用自前デコーダの二重経路。
- 条件: 16bit PNG の**画素**は Pillow の読み込み時点で 8bit 化される前提の経路で、どの変換（切り捨て／スケーリング）になるかテストが無い。Stealth は生の 16bit から正しく読むが、本体画素の扱いは別問題として未確認。
- 見立て: 頻度 低（16bit PNG 自体が少数）／重大度 中（「16bit 対応」の範囲が Stealth だけなのか画素もなのかが曖昧）。

#### BUG-11 アニメーションの loop／duration 意味論の等価性が未検証 ― 要実測
- 場所: `convert_image()` の loop 引き継ぎと `round(duration)`。
- 内容: GIF のループ回数の意味論と WebP の ANIM loop の意味論が一致するか、duration の丸め（Python の `round` は銀行丸め）で 1ms ずれる端数ケースがあるかは、フィクスチャで確認されていない。
- 見立て: 頻度 低／重大度 低〜中。

#### BUG-12 `missing_duration_ms` の変更で静止画 PNG／GIF まで再変換される
- 場所: `settings_signature()`（§1.5）。
- 内容: `missing_duration_ms` は拡張子が `.png`／`.gif` の変換ジョブにアニメーションかどうかを問わず含まれるため、この設定を変えると静止画 PNG／GIF も全件再変換の対象になる。
- 見立て: 頻度 低（設定変更時のみ）／重大度 低（結果は正しく、無駄な再変換だけが起きる）。
- 対応方針: Rust 版でも維持する。再利用判定の時点でファイルを開いてアニメーションかどうかを判定すると、判定自体のコストが「負ケースを安く保つ」原則に反するため（§3.7）。

#### BUG-13 piexif 往復で落ちるタグは保存後検証でも検出できない
- 場所: `prepare_metadata()` の piexif.load（辞書化）と `verify_metadata()` の期待値の作り方（`piexif.load(piexif.dump(exif_dict))`）。
- 内容: 期待値が往復後の値で作られるため、往復で落ちたタグは期待値にも出力にも無く、不一致として検出できない。タグが落ちる主経路は検証側の dump ではなく読み込み側の辞書化にあるとみられるが、これは仮説である（piexif.load の通常動作では未知タグは数値 ID で残り、不正な構造では例外になるため、具体的にどのタグが黙って落ちるかは Phase 0 のフィクスチャで確定する）。`doc/plan.md` の「黙って捨てない」方針に対して、落ち方が静かなままになる経路がある。
- 対応: §3.5（D-EXIF、Phase 2）。
- 見立て: 頻度 低／重大度 低〜中（保持範囲の正確な把握は D-EXIF の検証で別途行う）。
- 対応方針: Rust 版でも検証方式は現行踏襲とするが、この検出限界を仕様として明記する（§3.5）。保持範囲そのものは D-EXIF で実データにより確定する。

### 2.2 性能（PERF）

#### PERF-01 処理全体が逐次実行で、並列化の余地が丸ごと残っている
- 場所: `main()` のジョブループ。
- 条件: 常時。WebP エンコードは CPU 律速が本命候補（§4 の仮説 H2。要実測）。
- 見立て: 頻度 高／重大度は仮説 H2（エンコードが処理時間の大半を占める）が真なら高。並列化の効果自体は §4 で計測して確定する。

#### PERF-02 Stealth の負ケース（Stealth 無し）が 16bit PNG で特に重い
- 場所: `stealth_text()` → `png_16bit_pixels(path, header_only=True)`。
- 条件: `preserve.metadata = true`（既定）の全 PNG が対象。16bit の場合は、ヘッダ 152bit を見るためだけに IDAT 全体の zlib 展開（Python 実装のチャンク読み＋展開）が走る。8bit の場合は変換でどうせデコードする画素への 152 回のサンプルアクセスで済むため軽い。
- 見立て: 頻度 低〜中（16bit PNG の割合に依存）／重大度 中〜高（Stealth を持たない大多数の 16bit 画像に税金がかかる。「負ケースを安く保つ」原則に反する代表例）。

#### PERF-03 Stealth ありの 16bit PNG は Python のバイト単位フィルタ復元が全画素分走る
- 場所: `png_16bit_pixels()` の復元ループ（行×列×チャンネルの純 Python ループ）。
- 条件: Stealth を持つ 16bit PNG のペイロード復号時（2回目の全量デコード）。
- 見立て: 頻度 低／重大度 高（大きな画像では秒〜分単位になりうる。要実測）。

#### PERF-04 アニメーションの全フレームをメモリに保持する
- 場所: `convert_image()` の `frames` リスト（各フレームを `image.copy()` して保持）。
- 条件: フレーム数×フレームサイズに比例してメモリが増える。長尺 APNG／GIF で顕著。
- 見立て: 頻度 中／重大度 中〜高（並列化した場合は並列度と掛け算になるため、Rust 化では設計上の制約になる）。

#### PERF-05 `verify_metadata()` が全変換ファイルで出力を開き直す
- 場所: `verify_metadata()`。
- 条件: `preserve.metadata = true` の全変換。画素デコードはしない（Exif／ICC／XMP の比較のみ）ため絶対量は小さい見込みだが、件数が多いバッチでは積み上がる。要実測。
- 見立て: 頻度 高／重大度 低。

#### PERF-06 色正規化でフレームごとに sRGB プロファイル生成が走る経路がある
- 場所: `normalize_color()`（CMYK／L／LA＋ICC の場合に `ImageCms.createProfile("sRGB")` をフレームごとに生成）。
- 条件: ICC 付き LA／L の APNG など。頻度 低／重大度 低。

#### PERF-07 コピーが Windows ではバッファ読み書きになる
- 場所: `run_job()` のコピー経路（`shutil.copyfile`）。
- 条件: Python 公式ドキュメントによれば `shutil.copyfile()` は 3.8 以降、POSIX ではプラットフォーム固有の fast-copy（`os.copy_file_range()` 等）を内部で使う。素朴なバッファ読み書きになるのは実質 Windows 経路だけであり、主対象が Windows のため本ツールでは該当する。`copy.other_files` で大きなファイル（WebM 等）を扱う場合に効きうる。要実測（効果はファイルシステム依存）。
- 見立て: 頻度 中（Windows のみ）／重大度 低。

### 2.3 仕様・移植上の注意（SPEC）

#### SPEC-01 WebP オプションは quality だけで、method／lossless／exact が無い
- Pillow 既定の method は静止画 4、アニメーション 0 と非対称で、速度／サイズの調整手段が利用者に無い。Rust 化では libwebp の全設定（`WebPConfig`）へアクセスできるため、§7 項目1 で設定項目として追加することが決定済み。
- 見立て: 頻度 中／重大度 低（現行仕様の制限であり不具合ではない）。

#### SPEC-02 衝突判定の `casefold` は Python 固有の意味論
- Rust の `to_lowercase` と Python の `casefold` は一部文字（ß 等）で結果が異なる。該当するファイル名は稀だが、命名互換を厳密に取るなら差分を Phase 0 で列挙する。
- 見立て: 頻度 低／重大度 低。

#### SPEC-03 Stealth の alpha チャンネル指定に Python の負インデックス（-1）を使う箇所がある
- `stealth_text()` の modes 定義（`[-1]` は最後のチャンネル＝alpha の意味）。Rust へ移植する際は明示的なチャンネル番号へ置換しないとそのままでは書けない。移植時の取り違えポイントとして明記する。
- 見立て: 頻度 ―（移植時の注意）／重大度 中（取り違えると Stealth の復号が静かに壊れる）。

#### SPEC-04 adopt の優先順位は仕様として固定されている
- 再利用 → adopt → 通常処理の順で、`overwrite_existing = false` でも adopt が有効なら未登録の既存出力が登録される。これはテストで固定された意図的な挙動であり、Rust 版でも変えない。なお adopt 分岐に到達するのは `reuse_unchanged = true` かつ `adopt_untracked = true` の両方が真のときだけで、`reuse_unchanged = false` では adopt は一切効かない。
- 見立て: 頻度 ―（移植時の注意）／重大度 中（順序や前提を取り違えると互換が崩れる）。

## 3. Rust 化の設計

### 3.1 方針

1. **互換を先に固定し、高速化は計測で裏付けてから入れる。** 互換対象は §5 の表のとおり。出力 WebP のバイト一致は目指さない（エンコーダの版差でも変わるため）。目指すのは「同じ入力・同じ設定 → 同じ宛先・同じ意味の出力（画素・メタデータ・アニメーション）」。画素の等価性の合格基準は入力形式別に定める: デコード後の入力画素が現行と一致し、かつ ICC による色変換を経ない形式（静止 PNG／単一フレーム GIF 等の可逆デコード）では、libwebp の版とエンコード設定が同一なら出力画素の完全一致を要求する。アニメーション GIF のフレーム画素は disposal 合成を経て確定するため、合成の等価性が BUG-01 フィクスチャで確認できるまでは許容基準側に置く。入力画素自体がずれうる形式・経路（JPEG は IDCT／クロマアップサンプリングの実装差、16bit PNG は 8bit 化の方式差、L／LA＋ICC 等は CMS 実装への依存、APNG は disposal／blend 合成の丸め差）では、許容基準（画素差の統計量と閾値）を Phase 0 で定めて §4.2 に記録する。CMS 経路と APNG は Phase 0 の検証で等価性が確認できた場合に限り完全一致側へ移す。libwebp の版が異なる場合も同様に許容基準側で扱う。ファイルサイズは記録項目とし、合格基準には含めない（版差で正当に変わるため）。
2. **負ケースを安く保つ。** Stealth 無し・メタデータ無しの大多数の画像に、重い走査や再デコードを持ち込まない（PERF-02 の教訓）。
3. **単一 exe。** ユーザーの他 Rust ツールと同様、単一バイナリで配布できる構成にする。libwebp を C ソースからビルドする方式（§3.3 案A）はこの方針と両立するが、ビルド環境に C コンパイラが要る点は Phase 0 で確認する。
4. **互換の例外**: 16bit APNG は未対応とする（2026-11-27 決定。§3.4／§5）。16bit の静止画 PNG は対象に含む（BUG-10）。

### 3.2 クレート構成（単一バイナリクレート＋モジュール分割）


### 3.3 WebP エンコードの選択肢と検証結果

#### 案A: `webp` クレート（libwebp バインディング）― 本命
- 裏取り（docs.rs／配布ページ）: libwebp を `libwebp-sys` 経由で C ソースからビルドする。`Encoder::encode(quality: f32)`（lossy）、`encode_lossless()`、`encode_advanced(&WebPConfig)`（libwebp の全設定にアクセス可）、アニメーション用の `AnimEncoder`／`AnimFrame` がある。入力は RGB8／RGBA8（`image` クレートの `DynamicImage` からも生成可）。版は 0.3.1 を確認。
- 現行との関係: Pillow の WebP 保存も libwebp であり、エンコーダの系統が同じため、画素・サイズ・画質の等価性を最も取りやすい。method／lossless／exact はライブラリとしては初めて設定可能になる（§7 項目1 の決定により、利用者向けの設定項目として追加する）。
- アニメーションの method: Pillow のシーケンス保存は method 既定 0 だが、`WebPConfig` の既定 method は 4 で非対称である。互換のためフレーム側の `WebPConfig` には、未指定時の実効値として method = 0 を明示指定する（§7 項目1 で利用者が method を設定した場合は、その設定値が静止画・アニメーション双方で優先する）。アニメーションの lossless もフレーム側の `WebPConfig` へ反映する（実装とテストは Phase 4）。`WebPConfig` は必ず `WebPConfig::new()` 経由で初期化する（zeroed の config は検証で弾かれる）。
- 案A の既知の API 欠落（2026-11-27 に docs.rs のソースで再確認）: `AnimEncoder` は libwebp の `WebPAnimEncoderOptions`（minimize_size／kmin／kmax／allow_mixed）を公開しておらず、利用者は設定できない（内部の初期化既定値のまま使われる）。Pillow は minimize_size／kmin／kmax を別途計算して渡すため、この4項目は「Phase 0 で突き合わせる」対象から外し、設定不能な差異として記録する。bgcolor はクレート側の実効既定が 0（透明黒）で libwebp 既定の白と異なるため、`set_bgcolor` で明示設定する（Pillow 側の実効値は Phase 0 で確認する）。
- 静止画の経路: `encode_lossless()` は quality=75 固定で alpha_compression まで切り替える簡易経路のため使わず、lossy／lossless とも `WebPConfig` を自前で組み立てて `encode_advanced` に一本化する（§7 項目1 の method／exact を反映するため）。`Encoder::from_image` は Luma 系を Err にするため、入力は事前に RGB8／RGBA8 へ変換してから渡す。
- 注意: 静止画 `Encoder` と `AnimEncoder` のどちらにも、Exif／ICC／XMP の mux（コンテナへのメタデータ格納）API は確認できなかった。メタデータ格納は §3.5 の別経路で設計する。
- 注意: C ツールチェーン必須。Windows でのビルド可否は Phase 0 の最初の確認項目。

#### 案B: `image` クレート標準の WebP エンコーダ（`image-webp`、純 Rust）― 単独では不採用
- 裏取り（docs.rs の `image::codecs::webp::WebPEncoder`）: 「現状は **lossless エンコードのみ**対応。lossy が必要なら libwebp を使うこと」と明記されている。エンコーダは VP8L で、入力は Rgb8／Rgba8（これは `image` クレート経由の場合で、`image-webp` を直接使う場合は L8／La8 も受け付ける）。
- 判断: 既定 quality 90 の lossy 変換が本ツールの主用途であり、lossless のみでは置き換えにならない。将来、lossless モードを追加する場合の高速な代替候補として記録する（圧縮率は libwebp に劣ると同ドキュメントに明記）。

#### 案C: アニメーション専用に `webp-animation` クレートを併用 ― 原則不採用
- 裏取り（crates.io）: libwebp のアニメーション encode／decode のラッパで、土台は `libwebp-sys2`（案A の `libwebp-sys` とは別の sys クレート）。
- 判断: 案A の `AnimEncoder` で足りる見込みであり、libwebp のバインディングを2系統リンクすると版のずれとバイナリ肥大の元になる。案A のアニメーション API に不足が見つかった場合のみ再検討する。

#### 案D: 純 Rust の新興実装（`zenwebp`／`webpx` 等）― 初稿では不採用、Phase 0 のベンチ候補
- 裏取り（crates.io の `webpx` ページ）: `webpx` は libwebp バインディングで、同ページは後継として純 Rust の `zenwebp` を推奨するが、`zenwebp` は AGPL-3.0 または商用ライセンスと明記されている。本プロジェクトは MIT のため、ライセンス条件が合わない。なお一次資料間でもライセンス表記が揺れており、SPDX メタデータは AGPL-3.0-only、条文本体は or-later の文言になっている（2026-11-27 再確認）。
- 速度の裏取り（2026-11-27 追加確認）: `zenwebp` は crates.io 0.4.6、`#![forbid(unsafe_code)]` の純 Rust 実装で、`image-webp` のフォークが起源（なお `forbid(unsafe_code)` は完全ではない: docs.rs の Safety 節によれば、zenwebp 自身のソース内にも依存の proc-macro（archmage）経由で生成される unsafe があり、forbid を回避している。「純 Rust」でも unsafe が皆無という意味ではない）。開発元（Imazen）の公開ベンチでは lossy エンコードが libwebp 比で method 4 で 1.35 倍・method 6 で 1.32 倍、lossless は method 6 で 2.6 倍（いずれも開発元計測・当方の未実測）。一方で同じ開発元の `webpx` の docs.rs では「性能は実質互角で、写真によっては libwebp が最大約35%速く、逆に最大約2.5倍速い場合もある」とも書かれており、開発元資料の間でもばらつきが大きい。ユーザーのコーパスでの実測なしに「libwebp より速い」とは言えない。
- 出力サイズの注意（2026-11-27 追加確認）: 開発元の内部資料ではスクリーンショット系コーパスで libwebp 比 1.055〜1.068 倍（出力 5.5〜6.8% 増）の記録があり、採用条件 (2)（出力増 3% 以内）をコーパス次第で破る水準である。本ツールの主コーパス（AI 生成 PNG／スクリーンショット的な画像）と重なるため、条件 (2) は自コーパスの実測でのみ判定する。
- 安定性の裏取り: `zenwebp` は 0.4.x 系で 0.1.0 の公開が 2026 年と比較的新しく、lib.rs では「12 unstable releases（3 breaking）」、利用クレート数も少なく、実績面では libwebp や次項の `image-webp` 上流に及ばない。
- 安定だが範囲が狭い例: image-rs 上流の `image-webp`（0.2.4、MIT／Apache、依存クレート多数）は純 Rust で安定しているが、エンコーダは案B のとおり lossless のみで、しかも圧縮率は libwebp に劣る。「速くて安定」な純 Rust は現状 lossless 限定の話である。
- 判断: 本命には採用しない。Phase 0 で `zenwebp` をベンチ候補として実測対象に加える。採用範囲は静止画のみとし、アニメーションは採用の成否によらず案A（libwebp）のままにする（アニメーションの速度・サイズ・等価性は採用条件で検証しないため）。採用条件は次のすべてを満たすこと: (1) §4.2 のエンコーダ比較で対象コーパスの総時間が libwebp 比で 20% 以上短い、(2) 出力バイト数の増加が 3% 以内、(3) 出力画素が §3.1 の許容基準（Phase 0 で定める閾値）の内側にある、(4) ライセンス問題が解消している（商用ライセンスの取得かプロジェクトのライセンス変更かは §7 項目5 で利用者が判断する。ベンチが条件 (1)〜(3) を満たさなかった場合は項目5 の判断自体が不要になる）。純 Rust で lossy まで揃う MIT／Apache 系の選択肢が成熟したら判断を更新する。

#### 決定（初稿）
- **案A を本命**とし、Phase 0 で「静止画 lossy／lossless、アニメーション、Windows ビルド、メタデータ mux の別経路（§3.5）」を小さな試作で検証してから確定する（決定点 D-ENC）。検証に失敗した場合の退路は「libwebp-sys を直接使う薄いラッパを自前で持つ」であり、案B への全面切替はしない（lossy を捨てることになるため）。

### 3.4 デコード側の検証事項（Phase 0）

- GIF: `image` 0.25 の `GifDecoder` は disposal 合成済みのフレームを返す（2026-11-27 に docs.rs で再確認済み。当初想定していた「合成済みが得られない場合」の自前合成は不要）。残る差異候補は Disposal=Background の消去色（`image` は透明黒、Pillow は背景色）で、BUG-01 フィクスチャ（部分フレーム＋disposal 2/3、背景色が不透明なケースを含む）で合否を判定する。
- APNG: `default_image` の除外（除外後に保存フレームが0になる場合はジョブ単位の失敗として明示し、静止画として変換しない。除外後に保存フレームが1つだけの場合は静止画として保存する（現行どおり。loop の検証も走らない）。default_image のみの入力でのデコーダの振る舞いも含めて Phase 0 で確認する）、フレームごとの duration／loop の取得可否。不足する場合は `png` クレートでチャンク（acTL／fcTL）を直接読む経路を用意する。APNG のアニメーション読み取りには `PngDecoder::apng()` の明示呼び出しが必須である（通常経路は静止画として読む）。16bit APNG は `image` では未対応で、事前検査により未対応エラーになる確定した制限である（内部の `unreachable!` には通常到達しない）。対応可否は決定済み（2026-11-27）: **16bit APNG は未対応とする**。現行 Python 版は変換できるため互換の後退だが、受け入れる。検出したらジョブ単位の失敗として明示する（黙って静止画として読み込むことはしない）。対象は 16bit APNG のみで、通常の 8bit APNG は従来どおり変換対象とする。検出方法: デコード前に IHDR のビット深度を確認し、ビット深度が 16 でない時点で「16bit APNG ではない」と確定して acTL の走査はしない（短絡。8bit APNG の可能性は残る）。ビット深度が 16 の場合のみ acTL チャンクの有無を走査し、Stealth 走査やデコードより前に判定する。acTL の不存在の証明には最初の IDAT 到達までの走査が要るため、停止条件は最初の IDAT チャンクとし、payload はシークで飛ばす（負ケースのコストは、16bit PNG における最初の IDAT までのチャンクヘッダ走査分）。JPEG の SOF 走査も同様に、セグメントヘッダだけをシークで辿る。あわせて、デコーダ内部のパニック一般への備えとして、ジョブ境界で `catch_unwind` によりパニックをジョブ単位の失敗へ変換する（§3.6）。
- 16bit PNG: 画素の 8bit 化の方式（切り捨て／スケーリング）を Pillow の現行挙動とフィクスチャで突き合わせる（BUG-10）。Stealth 用の生デコードは現行どおり自前経路を移植する。
- PNG の CRC: チャンクの CRC 不一致を持つ PNG の扱いを Phase 0 の突き合わせ対象に含める（Stealth の生デコードは現行どおり CRC を検証しない。本体デコード側の扱いが現行 Pillow と同じかを確認する）。
- 拡張子と実際の形式の不一致は変換失敗とする（現行どおり。変換側で明示的に判定し、内容からの形式推定で成功させない）。MPO 形式は JPEG とは別形式として扱い、拡張子が .jpg でも形式不一致で変換失敗とする（現行どおり）。MPO の判定は MP 拡張（MPF）の APP2 マーカーの有無で行い、判定は第1段のヘッダ読み時点でジョブ単位の失敗とする。JPEG の SOF 精度が 8 でない入力も、第1段でジョブ単位の失敗とする（現行との突き合わせは Phase 0 で行う）。
- JPEG: Orientation は Exif から自前で読む（現行と同じ。取得元のフォールバックは形式共通の規則として §3.5 に置く）。CMYK JPEG のデコード結果の色の扱いを `color.rs` の検証対象にする。あわせて JPEG デコーダの実装差（現行 Pillow の libjpeg 系と Rust 側デコーダの IDCT／クロマアップサンプリング）による画素差をフィクスチャで測り、§3.1 の許容基準の入力にする。
- 寸法の事前チェック（BUG-07）: 変換の入口でヘッダから寸法だけを読み、一辺が WebP 上限（16,383）を超える入力はデコードや Stealth 走査の前に失敗として確定させる。アニメーションについてはフレームごとの面積も対象に含める（Pillow の上限はアニメーションでもフレーム面積に効くため）。なお Pillow の decompression bomb チェックは open 時点の先頭フレーム基準であり、総量側の遮断は予算マネージャが担う。
- 画素数の明示上限（BUG-08）: Rust 版は画素数の上限をコード側の明示値として持つ。値は Phase 0 で現行の Pillow 既定（decompression bomb の警告／エラー閾値）と突き合わせて決める（決定点 D-LIMIT）。Rust では確保失敗がプロセス終了になりうるため、上限による事前遮断が現行の `MemoryError` 捕捉の代替になる。D-LIMIT にはアニメーション用の総量上限も含める。1フレームが上限未満でもフレーム数が多ければ総メモリは無制限になるためである。仕組みは単一のメモリ予算マネージャに一本化する: 起動時に総量予算を一度だけ算出する（実行時に取得する利用可能メモリ連動。取得手段は決定点 D-MEM。Phase 0 で決めるのは値ではなく算出規則＝利用可能メモリの定義、割合、上限・下限のクランプ）。予算取得の対象は、再利用判定を通過した変換ジョブのみとする（コピージョブと再利用で終わるジョブは対象外）。取得と解放の主体はワーカープールではなく、集約側の単一ディスパッチャに一本化する（本書で「集約側」とはディスパッチャを指す）。再利用判定と adopt 判定はディスパッチャ側で第1段より前に行い、再利用／adopt で終わるジョブは第1段へ進まない。処理は2段に分ける: 第1段（ヘッダ読み取りと見積もり）は予算不要でプール上で並列に行い、第2段（デコード以降）はディスパッチャの許可後にだけプールのタスクとして生成する。第1段はヘッダとチャンク／セグメントのヘッダだけを読み、ファイル全体をメモリに載せない。読み方は形式で異なる: PNG／JPEG は payload をシークで飛ばす主体の走査、GIF はサブブロック単位（長さ1バイト＋最大255バイト）の逐次読みが主体になるため `BufReader` を前提とする。通知は固定長のメタ情報と、上限付きのエラー文字列からなる（変換結果のデータ自体はファイル経由で渡す）。通知には保存後検証の警告リストも含む（固定テンプレートの文字列で、件数の上限は8件（IFD 5種＋サムネイル＋ICC＋XMP）とする。警告テンプレートのバイト上限は D-LIMIT の対象として Phase 0 で決める）。エラー文字列の上限はバイト数で数え、D-LIMIT の対象として Phase 0 で決める。ERROR 行の型名部分は現行の Python 例外クラス名への写像を維持する（ConversionError 相当と OSError／PermissionError 等の OS エラー系を含む写像表（型名＋ライブラリ由来文面）を Phase 0 で固定する）。ERROR 行の本文は、写像で固定する範囲以外も現行の文面を維持する（ライブラリ由来の文面差は写像表の対象に含めて吸収する）。ただしワーカーのパニックでジョブ単位の失敗になった場合の ERROR 行本文は、現行に対応する文面が無いため実装裁量とする（型名部分は写像に従う。パニック由来の失敗の型名は、写像表に専用の対応を置いて Phase 0 で固定する）。切り詰めは文字境界まで後退して行い、切り詰めた場合は末尾に省略の印を付ける（現行は例外を全文出すため、切り詰め自体が意図的な変更であり §5 に挙げる）。滞留の上限はジョブ総数×（固定長＋エラー文字列の上限＋警告分（件数上限×警告テンプレートのバイト上限））であり、画像バッファに対して無視できる規模のため、通知の滞留分は予算対象外とする。第1段自体のメモリはプール幅×微量に収まる。第1段と第2段が同じプールを共有する場合は第2段を優先する（優先度付きキュー等で、許可済みジョブが未見積もりジョブの後ろに並ばないようにする。プール実装の評価は D-PAR で、rayon では優先が組めないため、その場合は段ごとに別プールとする構成になる）。完了通知のチャネルは無界とし、commit 中にワーカーが送信でブロックしない。「先着順」は第1段の完了順であり、計画順（§1.4 の casefold 順）とは一致しない。後続停止の「後続」も第1段の完了順で後に来る変換ジョブを指す。第1段の失敗は通常のジョブ失敗としてディスパッチャへ通知され、第2段へは進まない。第1段も `catch_unwind` の対象とし、結果通知が来ないジョブはリコンサイルと停滞打ち切りの対象に含める。中断時は状態（第1段実行中／見積もり待ち／許可済み未着手）を問わず、完了通知のあったジョブだけを記録し、他は未処理として次回に回す（現行の中断意味論と同じ。ただし2回目の中断の場合は §3.6 の例外がある）。ディスパッチャだけが帳簿を持つ単独の所有者で、見積もりを受け取って先着順に許可を出し、ワーカーからの完了通知で解放する。許可前のジョブはプールのタスクとして存在しないため、ワーカーが予算待ちでブロックすることは構造的に無く、プール枯渇の経路を持たない。帳簿が単一スレッド所有になるため、Mutex と poisoned の問題自体が発生しない。完了通知はジョブ ID と世代番号を持ち、ディスパッチャは現在の割当と一致する通知だけを解放に使い、重複・遅延した通知は無視する（成功通知と失敗通知の両着による同一割当の二重解放を防ぐ）。世代番号は割当ごとに単調増加で発行し、解放時にエントリを削除するため、解放後の遅延通知は一致先が無く無視される。ディスパッチャ自身がパニックした場合は、帳簿が失われた状態で続行せず、プロセス全体を終了コード 2 で終了する。各変換ジョブはデコード開始前に、ヘッダから見積もった必要量で予算の取得を試みる。見積もりの定義: 形式ごとに総デコードバイト数を求め（APNG は acTL のフレーム数×キャンバス寸法、GIF はブロック走査で数えたフレーム数×論理画面サイズ＝部分フレームもキャンバス寸法で見積もる、静止画は IHDR／SOF 等の寸法から1フレーム分）、保持フレームに加えて変換中の一時バッファとエンコーダの内部蓄積分を安全係数で寄せた量とする。見積もりに含める内訳は明示する: 保持フレーム、16bit の二重デコードで同時に生きる展開バッファと復元バッファ、合成／向き／色正規化の一時コピー、`AnimEncoder` の出力蓄積（入力保持とは別に全フレーム分）、メタデータ格納時のファイル全体ロード分。見積もりは実ピークの保証ではなく目安であり、Rust の確保失敗がプロセス終了になりうる点は、上限による事前遮断と合わせても完全には消えない。画素あたりの単価は保持フレームを RGBA8 換算の 4B/px とし、16bit PNG の生デコード分はサンプル深度×チャンネル数（色タイプ 2／4／6 で 6／4／8B/px）を別途加算する。安全係数は Phase 0 で現行 Python 版コーパスの実ピークメモリから暫定値を置き、Phase 5 の本計測で Rust 実装の実ピーク（ピークメモリは §4.2 の計測項目）を測って確定する（Python 側のピークの内訳は Rust 側のバッファ構造と対応しないため、Phase 0 の値は確定値にしない。Phase 4 の超過テストは暫定係数で行う）。見積もり自体が総量予算を超えるジョブはその時点でジョブ単位の失敗とし、予算の残量が足りないジョブは空きを待つ。待ちは先着順とし、予算不足で待っているジョブがある間は後続の変換ジョブの新規取得を止める（大きなジョブの飢餓を防ぐ）。この後続停止は変換ジョブ同士の話であり、予算対象外のコピー／再利用ジョブは待機列を迂回して投入できる（先頭の巨大な変換ジョブでコピー数千件が滞留することはない）。引き換えとして、待機中はワーカーが遊休化し、入力の並びによっては逐次実行より遅くなりうる。判定はデコード／保持に先立って行い、デコード中の累積チェック（フレームごとに、次フレームをデコードする前に累積値が見積もり前提と乖離していないか）を保険として併用する。乖離を検出した場合は追加の予算取得はせず、そのフレームのデコード前にジョブ単位の失敗とする。取得した予算はジョブ終了（§3.5 の保存後検証とメタデータ格納まで含む）まで保持する。解放はディスパッチャがジョブの終了を検知して行うため、ワーカー側の処理の成否やパニックに依存しない。解放漏れへの対策として、ディスパッチャは「実行中ジョブの集合」と帳簿を突き合わせるリコンサイルを持ち、完了通知の受信時と定期間隔で実行し、実行中ジョブが存在しないのに残っている割当は無効として回収する。待ち行列の先頭が長時間進まない場合の打ち切り（タイムアウトで実行全体を失敗として終了する）は、タイムアウト値を D-LIMIT の一部として Phase 0 で決める（終了コードは §5 で 2 に確定済み）。打ち切りが決まって初めて「解放漏れ1件で無期限に止まる故障モードを持たない」と言えるため、それまでは設計目標として扱う（ワーカー自体が固まるケースではリコンサイルは効かず、打ち切りだけが防衛線になる）。並列度と上限の相互依存はこの方式では生じない: 並列度はコア数基準のままで、実効的な同時実行数は予算の取得可否で決まる。Phase 4 までの逐次実行でも予算マネージャを同じ形で使い、1ジョブの上限は総量予算そのものである。ただし「Phase 4 で通った入力が並列化で新たに失敗することはない」とは言わない: Phase 5 の安全係数確定で見積もりが見直されれば成否が変わる入力がありうるし、停滞打ち切りは並列実行時にのみ効くため、逐次では成功した入力が並列実行では実行全体の失敗の対象になりうる。総量上限にも互換上の配慮を課す: 現行には総量上限が無くメモリが足りれば長尺でも変換成功するため、目安は「現行でもメモリ不足で失敗する規模」として Phase 0 で長尺コーパスのピークメモリを実測して算出規則を決める。予算は起動時に固定するため実行中のメモリ変動では成否は変わらないが、マシンや起動時点の状態が違えば成否が変わりうる点と、安全弁として失敗範囲が広がりうる点は §5 の意図的な変更に挙げる。テストでは予算をテストハーネスから内部指定で固定できるようにし（本番バイナリには環境変数・設定キー等の差し替え経路を持たない）、各 Phase の超過テストはそれを使う。超過時の扱い（ジョブ単位の失敗）は Phase 0 で決め、静止画分は Phase 1、アニメーション分は Phase 4 で実装とテストを行う。単体上限の値には互換上の制約がある: 現行は Pillow 既定の警告閾値（約 8,950 万画素）を超えても警告のみで変換が進み、失敗になるのはその2倍を超えた場合である。Rust 版の上限は現行のエラー閾値以上とし、現行で変換成功する画素数の画像を失敗させない。

### 3.5 メタデータの設計

- Exif の読み書き: 現行は piexif の読み込み→書き出しの往復で保持される範囲を正とし、往復で変わった IFD は保存後検証が警告として出す方式（往復が完全無損失であることは現行実装自身も前提にしていない）。Rust 側の候補は、読み書き両対応を謳う `little_exif`（lib.rs の一覧で WebP 対応・読み書き対応を確認）と、読み取り専用の `kamadak-exif`。採用条件は「現行の警告挙動と等価な範囲で保持できること」で、Phase 0 で実データ（A1111／NovelAI の実 PNG・JPEG）を使って検証する。保持範囲の確定は、生の TIFF 構造を直接パースした結果との突き合わせで行う（piexif 相当の往復だけでは落ちたタグが見えないため。BUG-13）。落ち方が問題になる具体タグのフィクスチャも Phase 0 で用意する。候補が条件を満たさない場合は、TIFF 構造の最小パーサ／ライタを自前で持ち、未知タグをバイト列のまま保持する方式に倒す（決定点 D-EXIF）。なお裏取りに使った `little_exif` 0.6.12 は現行版（0.6.23）より古く、現行版では書き込み時に Simple 形式を Extended へ変換する経路がある（読み込みは VP8X と EXIF フラグ（0x08）が立っていることが前提のまま）。版は Phase 0 で現行版に固定して再確認するため、ここでの役割分担は暫定とする: 役割は入力側 Exif の読み書きと TIFF バイト列の生成を第一候補とし、出力 WebP への格納と読み戻しは D-MUX 側で担保する。この前提は D-EXIF の Phase 0 検証項目に含める。
- sRGB プロファイル（PERF-06）: 色正規化で使う sRGB プロファイルはプロセス内で一度だけ生成して使い回し、フレームごとの生成をやめる。
- Orientation の取得元は形式共通で、Exif 辞書（0th IFD）を第一とし、無い場合は生の TIFF／Exif タグから直接読むフォールバックを持つ（現行の `getexif()` 相当）。
- PNG のメタデータ取得範囲（最初の IDAT の前後）は対象ごとに現行の実効範囲が異なるため、Phase 0 で対象ごとに確認して固定する（実測済みと未実測の切り分けは §1.6。具体的な範囲は §1.6 に記録し、Phase 0 で実測して更新する）。
- 生成テキスト（source_text）の規則は §1.6 の棚卸しどおりとする: 連結順序（PNG は parameters を先頭に、残りを info の辞書挿入順（重複キーを除きチャンク順））、各エントリの行形式は「キー: 値」、値が文字列でないエントリは黙って捨てる、空文字列の値も落とす、info の重複キーは最後の値が勝ち位置は最初の出現位置になる、XMP キーの除外判定は大小区別なしだが parameters の判定は完全一致という非対称、bytes の値は（PNG のテキストチャンクを除き）UTF-8 で復号し失敗したら latin-1 を使う（PNG のテキストチャンクは種別依存で、tEXt／zTXt は latin-1、iTXt は UTF-8。§1.6）。生成テキストの振り分けは、既存の UserComment が空ならそれに入れ、値があれば XPComment（UTF-16LE）へ回す。XPComment は値ではなくタグの存在で判定する（空の XPComment があるだけで変換失敗になる現行挙動を含む）。JPEG／GIF ではコメントを取得元とする（取得経路は Phase 0 で確定する。JPEG は COM セグメント、GIF はコメント拡張ブロックが候補。Stealth との結合分は Phase 3 で扱う。§6）。XMP の取得は `xmp` キーを優先し、値が空なら `XML:com.adobe.xmp` へ落ちる（いずれも完全一致・大小区別あり）。
- アニメーションの ICC: フレームごとに ICC が異なる場合は、最終フレームの値を出力全体の ICC とする（現行の意味論を維持する）。保存後検証の ICC 比較もこの値に対して行う。
- メタデータの WebP への格納: エンコード後に RIFF コンテナへ EXIF／ICCP／XMP チャンクを差し込む経路を別途持つ。候補は `img-parts` クレート（WebP の RIFF チャンク操作と `ImageEXIF`／`ImageICC` を確認）。ただし既知の制約として、`img-parts` には XMP の読み書き API（`ImageXMP` トレイト）が無く、XMP チャンクを手動で追加しても既存 VP8X の XMP フラグ（0x04）は立たない（フラグ再計算は ICC／EXIF の2ビットのみが対象で、クレート自身のテストが示す。2026-11-27 に docs.rs のソースで再確認）。アニメーション出力は常時 VP8X を持つため、この制約は必ず当たる。したがって D-MUX の検証は「格納できるか」ではなく「VP8X のフラグバイトと XMP チャンクを自前でどう書き換えるか」から始める（VP8X が無い静止画では、`set_exif` 等による VP8X 新規作成時にフラグが計算される経路もある。ただし XMP ビットが立つのは、XMP チャンクを挿入済みの状態で `set_exif`／`set_icc_profile` が呼ばれた場合のみである。格納の順序条件としてこの順序を守るか、順序に依存しないよう、格納後の検証で VP8X フラグバイトと実チャンクの一致を必ず確認し、不一致は補正するか失敗にする）。検証対象には静止画だけでなくアニメーション WebP（VP8X＋ANMF）への格納も含める（現行は `save_all` 時も保存オプションに exif／icc／xmp を含めているため）。
- 保存後検証（`verify_metadata` 相当）は Rust 版でも維持する。弱めるかどうかの判断は Phase 5 の本計測の結果を見て行う（最初から外さない。PERF-05）。なお現行の検証には BUG-13 の検出限界（piexif 往復で落ちたタグは検出できない）があり、Rust 版でも同じ限界を持つ。保持範囲の保証は検証ではなく D-EXIF の実データ確認で担う。
- ICC 変換（LittleCMS 相当）: 候補クレートの裏取りが初稿時点で取れていないため、Phase 0 の検証事項とする（決定点 D-CMS）。ICC 無しの CMYK は現行どおり単純変換でよいが、Adobe CMYK の反転仕様など Pillow の挙動との一致はフィクスチャで確認する。候補クレートの存在自体が確認できない場合は、Phase 2 の内数に落とさず、Phase 0 の中で lcms2 バインディング等の代替まで確定させる（Phase 構成の組み替えが必要なら Phase 0 終了時点で本書を改訂する）。

### 3.6 高速化の設計（並列化とボトルネック対策）

計測していない高速化の主張は本書に書かない。ここに書くのは構造の設計と、§4 で検証する仮説である。

- ジョブ単位の並列化: ファイル単位で独立な処理のため、ワーカースレッドプールでジョブを並列実行する。並列度は CPU コア数を上限の既定とする。メモリ制御は並列度をいじらず、§3.4 のメモリ予算マネージャに一本化する: 変換ジョブは見積もり量の予算を取得してから処理を始め、大きなアニメーション（PERF-04）は予算の空き待ちによって実効的な同時実行数が下がる。予算の取得はディスパッチャ側で行い、ワーカーは予算待ちでブロックしない（§3.4）。ジョブ境界では `catch_unwind` でパニックを捕捉し、ジョブ単位の失敗に変換する（デコーダ内部のパニックでプロセス全体を落とさないため）。ただし安全網の対象は純 Rust のデコード／メタデータ処理に限る。libwebp の FFI 呼び出し中・直後のパニックは、C 側状態の解放がクレートの Drop 実装依存で保証できないため、ジョブ失敗ではなくプロセス全体の終了に倒す（終了コード 2 は、メイン側で検出して明示的に終了することで実現し、パニック伝播による既定の 101 にしない。FFI 境界を跨ぐ unwind は対象外とする。Drop の挙動は Phase 0 の D-ENC 検証で確認する）。
- libwebp 内部スレッド（`WebPConfig.thread_level`）とジョブ並列の二重並列化は過剰購読になるため、原則はジョブ並列を主軸とし、`thread_level` は 0 を既定にする。単一巨大ファイルだけのケースで効くかどうかは §4 で測る。
- 中断（Ctrl-C）の扱い: Rust には KeyboardInterrupt 相当の既定機構が無いため、コンソール制御ハンドラ／シグナルで中断フラグを立てる仕組みを別途持つ（決定点 D-SIG）。ハンドラはプロセス起動直後に設置し、ハンドラ内ではフラグ設定のみを行う。ディスパッチャはジョブ境界と commit の合間にフラグを確認し、立っていれば §3.4 の中断時意味論（完了分のみ記録、終了コード 130）で畳む。ワーカー側もフレーム境界等の合間にフラグを確認し、立っていればジョブを未完了として中断する（長尺ジョブでも応答性を保つため。FFI のエンコード呼び出し中はその呼び出しの完了まで遅延しうる）。コピージョブもコピーのチャンク境界でフラグを確認する。16bit Stealth のフィルタ復元は行の境界でフラグを確認し、IDAT 展開はストリーミングで行って展開出力の単位量ごとにフラグを確認する（単位量は 1MiB とし、本書で固定する。単一の巨大な IDAT でも展開全体が無確認にならないようにするため。現行に相当する規定は無く、中断応答性と確認頻度の釣り合いで選んだ新規の設計値である）。確認点は初期化・計画段階にも置く。中断メッセージは現行の2種を使い分ける: 初期化・計画段階の中断は「中断しました。」、ジョブ実行段階の中断は「中断しました。記録済みのファイルは次回再利用されます。」とする。畳み処理中に2回目の中断を受けた場合は、最終 commit を行わず即時終了する（終了コード 130。中断メッセージは出す。この場合、未 commit の完了記録は残らない。§3.4 の中断時意味論の例外であり、§5 の意図的な変更に挙げる）。互換条件とするのは Ctrl-C（POSIX では SIGINT。SIGTERM の扱いは D-SIG で範囲を決める）であり、窓を閉じる（CTRL_CLOSE_EVENT）等はベストエフォートとして、畳み処理の完了と 130 は保証しない。フラグ確認が無いままプロセスが終了する経路を作らない。
- SQLite への書き込みは単一スレッドに寄せる: ワーカーは結果をチャネルで集約し、記録と commit バッチ（現行の `db_commit_every` の意味論）はメイン側で現行どおり行う。ワーカーから DB を直接触らない。DB エラー（commit の失敗、ディスクフル、DB ロック等）はジョブ単位の失敗にせず、現行どおりバッチ全体を打ち切って終了コード 2・専用メッセージ「処理履歴DBエラー: …」で終了する。並列実行時は、実行中ワーカーと未処理通知を中断時意味論に準じて畳んでから終了する。DB エラー時も最終 commit は試みる（現行の finally の構造を維持する）。ワーカーのパニック（ジョブ単位の失敗に変換されたもの）と停滞打ち切り時は最終 commit を試みる。ディスパッチャのパニック時と FFI パニック時は commit を試みず終了する（ディスパッチャのパニックは主体が失われるため。FFI パニックは境界でプロセスの状態が不定になるため、DB 操作を含む後続処理を行わない。§5 の意図的な変更 (14)）。メインスレッドがディスパッチャを担い、「メイン側」とはディスパッチャを指す。試みた commit 自体が失敗した場合はそのまま打ち切る。異常終了時（終了コード 2 の経路）と 2回目の中断時、初期化・計画段階で中断した場合は終了状態の記録を更新しない（「実行中」のまま残し、次回は掃除が走る）。帳簿・進捗・DB 記録はディスパッチャ（単一スレッド）が担うため、commit の間は解放と投入が止まる。この直列区間の影響は Phase 5 の計測項目に含める。
- 標準出力への進捗表示は行単位で競合しないよう集約側で出す（現行のメッセージ形式は §5 の互換対象）。表示用の相対パスは OS の区切り文字で出す（Windows では \。DB 保存・衝突判定の POSIX 表記とは別で、現行どおり）。標準出力・標準エラーへの書き込み失敗（閉じられたパイプ等）はジョブの成否に数えず、失敗した出力先については以後の表示を打ち切って処理を続行する（現行の二重計上や異常終了は再現しない。標準エラーへの出力は、書き込み失敗でパニックする `eprintln!` ではなく、失敗を無視する経路で出す）。
- Stealth の負ケース対策（PERF-02）: 16bit 経路は「IDAT 展開は避けられないが、フィルタ復元はヘッダ範囲だけ」という現行の段階構造を維持しつつ、展開と復元を Rust のネイティブ実装にすることで単体コストを下げる。具体的な削減率は書かず、§4 の H3 で測る。8bit Stealth の対象モード判定は、変換前の元の色タイプで行う（対象は色タイプ 2／4／6、すなわち RGB／LA／RGBA に限る）。APNG の Stealth は、フレーム巡回前の開いた直後のフレーム（既定画像を含む先頭フレーム）の画素から読む（現行どおり）。
- コピー経路（PERF-07）は現行の `shutil.copyfile`（内容のみのコピー）に意味論を合わせる。`std::fs::copy` は権限ビットまでコピーし無条件に上書きするため、そのままは使わない（入力が読取専用だとコピー先まで読取専用になり、日時設定や置換の失敗要因になる。Windows では代替データストリームまでコピーされる差異もある）。コピー実装は `File` 同士の内容コピーとし、読み取り側を `BufReader::with_capacity(64KiB)` で包んだ読み書きループでコピーする（転送単位は BufReader の容量と同じ 64KiB とする。64KiB は Windows での CPython の `copyfile` の単位に合わせた値。ループ形にするのは §3.6 のチャンク境界での中断確認のため）。一時ファイルへの書き込み順序は §3.8 に従う。`std::io::copy` は Linux では copy_file_range 等へ特殊化されうるため「高速 API を使わない」という表現はしない。避けるのは `fs::copy` の権限複写と Windows の CopyFile 系である。Windows での利得の主張は取り下げ、実測結果だけを §4 に記録する。

#### 3.6.1 高速化の上限（2026-11-27 追記）
- エンコード本体は現行 Python 版も Rust 版（案A 採用時）も同じ系統の libwebp（C 実装）であり、同一の libwebp 版・同一設定なら、言語を変えてもエンコード自体の単体速度は変わらない。C／C++ から直接 libwebp を叩いても同等が上限で、「Rust より速い言語」で得られる余地は実質無い。逆に libwebp の版が変われば速度も出力も変わりうるため、版は §3.7 のとおり変換ジョブのシグネチャに含め、§4.2 の計測記録にも必須とする。案D（`zenwebp`）採用時はこの前提が静止画については対象外になり、libwebp のままなのはアニメーションだけである（その場合の採否は §3.3 案D の採用条件で決着済みの話として扱う）。
- 案A 採用時、Rust 化で速くなるのは周辺側だけである: Python で書かれた処理（16bit Stealth の展開・復元、メタデータ処理、起動、並列制御）と、ジョブ並列化の実装しやすさ。案D 採用時は静止画エンコーダ自体の差し替えによる速度差が別途ありうる。
- 言語の外側で残る手段は、(1) エンコード設定の変更（method を下げる等。出力サイズ／画質とのトレードオフ）、(2) libwebp 内部スレッド（`thread_level`）、(3) エンコーダ実装そのものの差し替え（純 Rust 実装が libwebp より速いという主張はあるが未実測で、ライセンス上の制約は §3.3 案D のとおり）、(4) 処理自体を省くこと（Stealth 負ケースや保存後検証の見直し）。いずれも §4 の計測で裏付けを取ってから採否を決める。

### 3.7 状態 DB とシグネチャの移行

- 既存の `.img2webp.sqlite3`（スキーマ `user_version = 1`）はそのまま読めることを互換条件とする（`rusqlite` で同じテーブル定義を使う。既存テーブルの定義は同じとし、終了状態の記録用にメタテーブル `img2webp_meta` を追加する。§3.8）。既存 DB の user_version が 0 の場合は受理して 1 へ初期化し、0／1 以外（負値を含む）は拒否する（現行どおり）。状態 DB を新規作成する場合も、現行の初期化パラメータ（WAL、synchronous=NORMAL、user_version = 1）を設定する。接続時の busy timeout は現行の Python 既定と同じ 5秒とする。DB へ記録する stat は §3.8 の記録用 stat の値とする（記録値と変換内容の乖離時の帰結も §3.8）。
- 再利用判定はシグネチャ文字列の完全一致で行われるため、**コピージョブのシグネチャは現行の JSON 文字列をバイト単位で再現する**（キーソート、区切りなし、`pipeline: 2` を含む）。`platform` は現行の値域（`nt`／`posix`）へ対応付けて入れる（Rust の OS 名をそのまま入れると全記録が不一致になるため）。これによりコピージョブの再利用は移行後も効く。
- BUG-03 の対策（エンコーダ識別とパイプライン版の引き上げ）は**変換ジョブのシグネチャにだけ**適用する: 変換用は `pipeline: 3` とし、エンコーダ識別を追加する。識別の中身は D-ENC で確定したエンコーダに依存し、案A なら libwebp の版＋クレート版とする。退路（libwebp-sys を直接使う自前ラッパ）採用時は libwebp の版＋`libwebp-sys` の版とする。案D（`zenwebp`）採用時は採用範囲が静止画のみでアニメーションは libwebp のままになるため、両方の識別（`zenwebp` の識別子と版、libwebp の版＋クレート版）を併記する（ジョブ単位で使い分けることはしない。再利用判定でファイルを開かない現行の枠組みを保つため）。識別の範囲は「出力に影響する依存の版」と定義する: エンコーダ分に加えて、デコーダ群（`image`／PNG／JPEG デコーダ）、CMS 実装（D-CMS）、メタデータ処理系（D-EXIF で選ぶ Exif 書き込み手段。BUG-03 が挙げた piexif 分の対策）、格納実装（D-MUX）の版を含める。D-EXIF／D-MUX で自前実装に倒れた部分についてはクレート版が存在しないため、その実装の変更はパイプライン版の引き上げで吸収する。これにより移行時に変換済みファイルは一度だけ作り直しになる。ただしこの「一度だけ」はリリース版の話であり、開発中の Phase 1〜5 のバイナリ（リリース前）が実 DB に書くと、未実装機能（メタデータ等）の欠けた出力が正規記録として残る。そのため開発中は実 DB への書き込みを禁止し（開発用 DB のみを使う）、実 DB を扱うのは全識別を含むリリース版だけとする（2026-11-27 決定で確定。Phase ごとに pipeline を引き上げる代替案は不採用）。隔離はビルドで担保する: 開発ビルドは状態 DB のファイル名を開発用（`.img2webp-dev.sqlite3`）に変えるため、実 DB には書けない。切り替えは Cargo の feature（`dev-db`）で行い、debug／release の別とは独立させる。`dev-db` は**デフォルト feature** とする: 開発中の通常のビルド（`cargo build --release` を含む）はそのまま開発ビルドになり、付け忘れでは崩れない。外すのは Phase 6 のリリースビルドで `--no-default-features` を明示した場合だけであり、リリースビルドで `--all-features` は使わない。`dev-db` は最終バイナリクレートだけに置く（default の集合は dev-db のみとし、外す変更も追加する変更も本書の改訂対象とする。`--no-default-features` は default 全部を外すため、追加した feature がリリースビルドで黙って脱落する経路を作らないためである）。開発ビルドは起動行に、開発ビルドである旨と実効の DB 名・出力先を表示する（表示は標準エラーへ出す。開発ビルド専用の表示で、リリースビルドの出力形式互換には影響しない）。起動行の文言は `img2webp (開発ビルド): 状態DB=<実効パス>, 出力先=<実効パス>` の1行に固定する。隔離の射程は DB だけではない: 開発ビルドは出力フォルダも開発用に差し替える（config の output_dir 名に `-dev` を付けた兄弟フォルダ）。差し替えは、パスを現行と同じくリンク解決（symlink／ジャンクション（§3.8 の定義）の解決を含む）した後に行い、実効パスに対して現行と同じ入力／出力の同一・親子チェックを再適用する（一致または配下ならエラー。チェックは §1.3 の方式＝Windows では小文字化し、親子判定はパス要素単位で行う）。リンク解決は現行の `Path.resolve()` と同じ非 strict の意味論とする: 存在する最深の祖先まで解決し、残りは語彙的に繋ぐ（Rust の `canonicalize` は存在しないパスでエラーになるため、そのままでは初回実行＝出力フォルダが存在しない通常経路で失敗する）。Windows の verbatim パス（`\\?\` プレフィックス）は剥がして通常表記に戻してから、比較・保存・表示に使う（UNC は `\\server\share` 形式を正規形とし、DB へ保存する相対パスの計算・表示・比較はすべて正規形で行う。Phase 0 のフィクスチャに UNC パスの入力ケースを含める）。派生先フォルダは利用者が config に書いた場所ではないため、開発ビルドはそのフォルダが開発用出力である旨のマーカーファイルを置く。マーカーファイルの名前は `.img2webp-dev-output` とし、内容は `img2webp development build output folder` の1行に固定する（文面の変更は本書の改訂を経る）。既存ファイルの読み取りに失敗した場合は「内容不一致」として扱う（WARN＋非上書きで、マーカーとしては扱わない）。作成は起動時に存在しなければ行う（起動ごとに再試行の契機を持つ）。同名ファイルが既にある場合は、内容がマーカー文面と一致する場合のみマーカーとして扱い、一致しなければ WARN を出して上書きしない（利用者ファイルをマーカーと誤認しない）。配置に失敗した場合は WARN を出して続行する。マーカー名も宛先の予約集合に含める（帰結は DB 名の予約と同じ連番リネームであり、入力自体は処理される。予約が効く範囲は入力ルート直下のみで、サブフォルダ内の同名ファイルは通常ファイルとして扱う。両ビルドに適用する）。リリースビルドでは `-dev` フォルダとマーカーは残置され、状態としては読まれない。output_dir がドライブルート等でフォルダ名を持たない場合は `-dev` を付けられないためエラーにする。入力フォルダ内への書き込みは行わない（フォルダ自体の作成は §3.8 のとおり。マーカーの配置も出力側のみである）。宛先の予約集合には、実 DB 名と開発用 DB 名の双方（各々に `-wal`／`-shm`／`-journal` を付けた計8種）を含める（どちらのビルドでも両方を予約し、相手側の DB ファイルが入力にあっても宛先にしない）。入力フォルダ内に残った開発用 DB ファイルは、リリース版では状態 DB として開かれず、予約により変換／コピーの宛先にもならない。既定値（method 等）は §7 項目1 で確定しており、正本はコード内定数である（同梱 config.ini テンプレはその複写）。Phase 5 の掃引で変更が妥当となっても自動では変えず、利用者の再決定と本書（§7）の改訂を経て変更し、その場合はゴールデン文字列を再固定する（再固定は変更を含む作業の完了条件とする）。識別の版の値はビルド時に `Cargo.lock` から自動で埋め込む（手書き定数は禁止する。手書きだと版の更新時に識別だけ古いまま残る故障モードを作るため）。埋め込みの方法は決定点 D-LOCK として定める: build.rs が、環境変数 `CARGO` で渡される cargo を使い、`cargo metadata --locked --offline`（解決の起点は `--manifest-path` で自パッケージとし（出力はワークスペース全体の解決グラフで、対象クレートの版はその中から取る）、外側ビルドと同一の feature 集合を渡す。feature 集合は build.rs が `CARGO_FEATURE_*` 環境変数から再構成する。再構成は、自パッケージの feature 定義一覧（Cargo.toml の `[features]`）と突き合わせて元の名前へ復元する（環境変数名への変換は一方向で、`dev-db` と `dev_db` のような `-`／`_` の差は定義一覧との照合でしか戻せない）。`CARGO_FEATURE_DEFAULT` が無い場合は `--no-default-features` を付けて、リリースビルドの状態を再現する）で得た解決グラフから対象クレートの版を取得してコンパイル時に埋め込み、Cargo.lock の変更で再ビルドされる宣言（rerun-if-changed）を含める。lock の探索先はクレートルートの Cargo.lock とする（構成がワークスペース化した場合はそのルート）。対象クレートの確定リストは Phase 0 で本書に固定する。libwebp 本体の版は Cargo.lock には無いため、libwebp-sys が束ねる C ライブラリの版を build.rs のプローブで取得する。システムリンクのライブラリ（lcms2 等）も同様にプローブ対象とするが、プローブで得られるのはビルド機の版であり、動的リンクでは実行時の版と一致する保証が無い。そのため D-CMS の条件として、CMS はソース同梱または静的リンクを原則とし、動的リンクになる場合は版を実行時に取得してシグネチャへ入れる方式へ切り替える（どちらかは Phase 0 で確定する）。実行時取得の場合は、起動時に1回だけ取得して計画段階より前に確定させ、シグネチャには取得した整数値（例: lcms2 の 2.17 は 2170）をそのまま入れる。動的リンクを採用した場合は配布物が exe＋DLL になり §3.1 方針3（単一 exe）の例外となるため、その旨を D-CMS の決着に記録し、Phase 6 で同梱 DLL の構成を確認する。ロード方式は D-CMS で確定する: 直接リンクの場合は DLL 不在が起動自体の失敗になるため取得失敗の分岐は持たず、動的ロード（libloading 等）の場合に限り、失敗時はビルド時プローブと同じ代替マーカーを入れる。マーカーと実数値の間でシグネチャが変われば全件再変換になる（両方向とも）。実行環境の DLL 差し替えで値が変われば全件再変換になる（§5 の意図的な変更に含める）。プローブで取得できない場合はクレート版等で代替し、識別に代替マーカーを含めて通常ビルドと区別できるようにする（代替の有無が埋もれないようにするため）。`[patch]`／path 依存は版文字列ではソース差し替えを検出できないため、使う場合は識別にその旨のマーカーを含め、変更時はパイプライン版の引き上げでも吸収する。feature 選択が出力に影響する自クレートの feature は、版と合わせて有効な集合も埋め込む（再構成は自クレート分に限る。依存クレート側の有効 feature はこの方法では得られないため、依存側の feature 切り替えが出力に影響する場合はパイプライン版の引き上げで吸収する）。Cargo.lock はリポジトリにコミットして管理する（バイナリクレートのため）。リリースビルドでは `--locked` を必須とする（Phase 6 の確認項目）ため、lock が無い環境ではビルド自体が失敗する（安全側に倒れる。保証されないビルドが流通する経路は無い）。依存のパッチリリースでも版が変われば全件再変換になる点は保守上の逆インセンティブになりうるが、出力の同一性を優先して受け入れる（§5 の意図的な変更に含める。パッチ版まで含める方針の維持は 2026-11-27 決定で確定）。
- シグネチャ項目の新旧対応: `pipeline` はコピー用 2 のまま／変換用 3。`missing_duration_ms` は現行どおり拡張子 `.png`／`.gif` の変換ジョブに含める（BUG-12）。`quality`／`metadata` は現行どおり変換ジョブのみの項目で、コピー用には含めない。それ以外の項目（`platform`、`action`、timestamps）は現行のキーと値域をそのまま使う。§7 項目1 の決定により追加される lossless／method／exact を含め、出力に影響する新設定はすべて変換シグネチャへ含める（既定値の場合も省略しない）。ただし入れるのはファイルを開かずに決まる値に限る: 未指定の項目は「未指定マーカー」ではなく、その時点のプログラム既定値を展開して入れる（未指定のまま既定値が変わればシグネチャが変わって再変換される。既定値変更を検出できない穴を作らない）。method のように実効値がジョブ種別で変わる項目は、種別ごとの実効値を別キーで両方入れる（静止画用／アニメーション用。どちらもファイルを開かずに決まる）。exact のようにジョブ種別によっては出力に影響しない項目も、種別をファイルを開かずに判定できない場合は一律に含める（無駄な再変換を承知で含める。BUG-12 と同じ扱い）。
- シグネチャ文字列の実例（ゴールデン）: コピーは `{"action":"copy","pipeline":2,"platform":"nt","timestamps":true}`。現行の変換用はこれに quality／metadata が加わり、`.png`／`.gif` では `missing_duration_ms` も加わる。Rust 版の変換用は `pipeline: 3` と識別項目が加わる形とし、Phase 1 で暫定形の実例を、Phase 2 で識別追加後の最終形を本書に固定する（ゴールデンの対象はビルド時埋め込みで決まる項目の形とし、実行時取得の値＝動的リンク時の CMS 版は実行ごとに変わりうるため対象外とする）。
- レコード全体の一致: 再利用判定はシグネチャだけでなくレコード全項目（宛先の相対パス、入力のサイズ／mtime／ctime、出力のサイズ／mtime）の完全一致である。Rust 側の値の作り方は現行に合わせる: 相対パスは OS によらず POSIX 表記（`/` 区切り）で保存する。時刻は Python の `st_mtime_ns`／`st_ctime_ns` と同じく Unix エポックからのナノ秒で、ctime の意味も OS に従う: POSIX では inode のメタデータ変更時刻を Unix 拡張メタデータから取り、Windows ではファイルの作成日時を取る。ctime／作成日時の取得手段が無い環境では、そのジョブは再利用対象にせず変換し直す（取得不能を不一致として扱い、静かな劣化にしない）。取得不能な環境では毎回全件再変換になるため、起動時に WARN を標準エラーへ出して再利用が効かないことを利用者に知らせる。取得可否は Phase 0 で確認する。

### 3.8 ファイル出力と日時

- 宛先がシンボリックリンクの場合: 事前チェックと再利用／adopt 判定はリンク追随で行う（現行どおり）。最終確定はリンク先ではなくリンク自体を置換する（有効なリンクでも同じ）。壊れたシンボリックリンクは「存在しない」扱いとし、置換は最終確定の直前にリンクを unlink してから配置する手順とする。unlink の後に同名のエントリが作られた場合はジョブ単位の失敗とする（この窓では上書き不可の保証は崩れる）。配置に失敗した場合は元のリンクは失われる（現行の原子的置換との差異であり、§5 (9) の例外として挙げる）。この unlink 手順は `overwrite_existing = false` の原子操作の経路に限る（`true` の場合は通常の置換でリンク自体を置換する）。
- 宛先にディレクトリが存在する場合は、`overwrite_existing = false` なら SKIP、`true` ならジョブ単位の失敗とする（現行どおり）。
- フォルダ作成: 入力／出力フォルダは起動時に作成する（存在しない input_dir は作成して0件で正常終了する。現行どおり）。作成は §3.7 の差し替えと再検証を終えた実効パスに対して行う（開発ビルドでは -dev フォルダが作成対象になる）。起動時の作成に失敗した場合（output_dir に既存ファイルが指定されている等）は、現行どおり設定エラーとして「設定エラー: …」の文言形式で終了コード 2 で終了する。宛先の親フォルダはジョブごとに作成する（入力のサブフォルダ構造を出力側に作る現行挙動）で、その作成の失敗はジョブ単位の失敗として数える（現行どおり）。作成は既存を成功とみなす方式（create_dir_all 相当）で行う（並列実行時に同じ親フォルダの作成が競合しても敗者が失敗にならないため）。
- 入力の再確認: 変換ジョブについては、第2段の開始時に、ヘッダから読む寸法・フレーム数・形式・ビット深度（色タイプ／コンポーネント数）を第1段で読んだ値と突き合わせ、異なればジョブ単位の失敗とする（文言は再 stat 失敗と同じ「処理中に入力ファイルが変更されました」とする。第1段と第2段の間の入力差し替えで、上限チェックと見積もりの裏付けが崩れるのを防ぐ）。第2段の値はデコーダの返値ではなくヘッダ再読みで得る（第1段と同じ読み方をする）。フレーム数は、APNG は acTL の値、GIF はブロック走査の生数で両段を統一する（default_image 除外後の数ではない）。形式は §1.4 の拡張子分類と同じ区分とし、APNG は PNG と同一形式として扱い（アニメーション性はフレーム数で区別する）、MPO は JPEG と別区分とする。ビット深度は第1段で、PNG は IHDR、JPEG は SOF の精度から記録し、GIF は対象外とする。変換／コピーの完了前にソースを再 stat し、size／mtime／ctime が処理開始時と異なればジョブ単位の失敗とする（「処理中に入力ファイルが変更されました」。現行どおりで、出力は置換されない）。処理開始時の stat は第2段の開始時点で取る（コピージョブはコピー開始時点）。ただし記録に使う stat（出力へ付ける日時を含む）は第1段の開始前に取る（第1段のヘッダ読みで入力の atime が更新されても、出力へ付ける atime が変わらないようにするため。コピージョブの記録用 stat はコピー開始時点のものとする）。変更検出の突き合わせは size／mtime／ctime で行い、基準は第2段開始時点の stat とする（コピージョブではコピー開始時点の stat。記録用 stat は検出の基準にしない。atime は検出対象に含めないため、第1段の読み取り自体は検出対象の変更に数えず、検出の実効ウィンドウは第2段開始時点からになる）。DB へ記録する stat は記録用 stat の値とする（adopt で記録する stat は、入力側は adopt 判定時点の入力 stat、出力側は判定時点の既存出力の stat とする）。記録用 stat の取得後に入力が変更されたジョブが成功した場合、記録値と変換内容が乖離しうるが、次回実行では入力の stat が記録値と一致しないため再利用されず作り直される。
- 一時ファイル＋原子置換の方式は現行を踏襲する。一時ファイルへの書き込みは空のファイルへオフセット0から行い、ハンドルを閉じてから日時付与と置換へ進む。失敗時・中断時は一時ファイルを削除する。即時終了経路（2回目の中断等）で残った一時ファイルは、次回実行の起動時に命名形状で識別して削除する（出力フォルダへの蓄積を防ぐ）。一時ファイルのプレフィックスは `.img2webp-` に固定する（本書で固定し、変更は本書の改訂を経る）。命名はプレフィックス＋ランダム部＋宛先のサフィックスの形状とし、識別はこの形状で行う（宛先のサフィックスが空（拡張子なし）の場合も含む）。ランダム部は英数字＋アンダースコアの8文字に固定する（現行 Python 版の tempfile 既定と同じ形状とし、移行直後に Python 版が残した一時ファイルも識別の対象に含める）。掃除の対象からは §3.7 の予約集合（状態 DB 名8種とマーカーファイル名）を除外する（開発用 DB 名とマーカーファイル名はプレフィックスに文字列として一致するため）。削除対象は、命名形状に一致し、かつ状態 DB に完了記録が無いものに限る（正規の利用者出力は記録があるため、一時ファイル形状の名前でも対象にならない）。記録の有無は、ファイルの出力相対パス（POSIX 表記）を、completed_jobs の各記録の宛先（格納値）と突き合わせて判定する（宛先は記録時に確定した値であり、導出はしない。大小文字の扱いは衝突判定と同じ規則（casefold）に従う）。プログラムが置いていない未追跡の既存ファイルが一時ファイル形状の名前を持つ場合も、記録が無いため削除対象になる（`overwrite_existing = false` かつ adopt 無効でも起動時掃除では削除される。既知の例外として扱う）。この保護は状態 DB が出力と対応していることが前提であり、DB だけを差し替えた場合は正規出力が削除対象になりうる（運用上の注意として、Phase 6 の README 移行注意に含める）。また、中断や DB エラーで「置換済みだが未記録」になった正規出力はこの保護の対象外であり、一時ファイル形状の名前を持つ場合は削除されうる（既知の例外として扱う）。起動時の掃除の対象は各ビルドの実効出力先の配下（サブフォルダを含む。ディレクトリへのシンボリックリンクは辿らない）で、削除対象は通常ファイルとシンボリックリンク（リンク自体を削除し、リンク先には触れない）に限る（ディレクトリとジャンクション（Windows のジャンクションを指し、ディレクトリへのシンボリックリンクとは区別する）は対象にしない。ディレクトリへのシンボリックリンク自体は、命名形状に一致すれば削除対象に含める）。シンボリックリンクの作成時刻はリンク自身のものを使う（壊れたリンクでもリンク自身の時刻で判定する）。走査ではジャンクションも辿らない。作成時刻が起動時刻より前で、かつ最低経過時間（値は D-LIMIT で Phase 0 に決める。想定最大ジョブ時間を下回らない値とする）を経過したものに限る。作成時刻が取得できない場合は掃除対象から外す（消さない）。作成時刻は Windows では作成日時の付与（日時引き継ぎ）でプログラム自身が書き換える値であり、年齢ガードはその前提で効く範囲に限る（この前提は通常ファイルについてのもので、シンボリックリンクには日時引き継ぎを行わないため、リンクの作成時刻はプログラムが書き換えない）。同一出力先への同時実行は前提としない。削除に失敗した場合は無視して続行する。掃除の省略: 前回の実行の終了状態を状態 DB に記録する。格納はメタ情報用の新規テーブル `img2webp_meta` とし、user_version は 1 のまま据え置く（Python 版は追加テーブルを無視でき、DB を開ける前提を保つ）。テーブルは DB 初期化時に IF NOT EXISTS 相当で常に作成する（読み取り手順の前に存在が保証される）。作成の失敗は初期化段階の DB エラーとして終了コード 2 で終了する。手順は「読み取り→前回が正常終了かの判定→『実行中』へ倒す」の順とし、起動時の倒しと正常終了時の更新は即時に単独で commit する（倒しはジョブ処理開始前に commit 済みとする）。倒しの書き込みが失敗した場合は初期化段階の DB エラーとして終了コード 2 で終了する。正常終了は終了コード 0／1 と、正しく畳めた中断の 130 を指す（ここでいう中断はジョブ実行段階のもので、初期化・計画段階の中断は含まない。§3.6）。記録が存在しない場合（Python 版が作った DB への初回起動等）は「正常終了でない」として扱い掃除を走らせる。DB エラーで記録の更新自体が失敗した場合は「正常終了でない」側に倒れ、次回は掃除が走る。正常終了時の終了状態の更新が DB エラーで失敗した場合は、ジョブ処理の結果にかかわらず DB エラーとして終了コード 2 とし、DB エラーの専用メッセージを出す（次回は掃除が走るため、実害は掃除の再実行に限られる）。記録には正常終了時点の completed_jobs の件数を持たせ、次回起動時に現在の件数と異なれば「自プロセス以外の処理が DB に触れた」とみなして記録を信用せず掃除を走らせる（Python 版を挟んだ場合の陳腐化対策。自プロセスの正常終了に伴う書き込みやチェックポイントでは件数は変わらないため発火しない）。終了状態の更新（件数の取得を含む）は、残りのジョブ記録の最終 commit の後に行う。検出範囲は件数が変わる他者書き込みに限られ、既記録パスの更新のみの他者実行や、commit に至らなかった他者実行は検出できない（その場合の残骸は最低経過時間の10倍ルールが受け皿になる）。前回が正常終了の場合は掃除を省略できる（省略時も走査自体は行い、削除対象を絞る）が、最低経過時間の10倍を超える古さのものは省略時でも対象にする（倍率は本書で固定し、変更は本書の改訂を経る。残骸が永続化しないため）。掃除の時刻条件（最低経過時間とその10倍の閾値、現在時刻）は、テストハーネスから内部指定で差し替えできるようにする（本番バイナリには差し替え経路を持たない。予算マネージャのテスト指定と同じ扱い）。一時ファイルの権限は通常の作成権限（umask 準拠）にし、BUG-04 を移行時に直す（意図的な挙動変更として §5 に明記）。なお `tempfile` クレートは全 OS で既定がプライベートな権限のため、使う場合は `Builder::permissions` 等で権限を明示指定しないと BUG-04 をそのまま再現する点に注意する。また `permissions()` の指定は Windows ではほぼ効かず、readonly 指定では作成自体が失敗するため、BUG-04 の解消は主対象の Windows で別途確認する（POSIX の umask 準拠だけでは完了にしない）。
- `overwrite_existing = false` の場合（BUG-05）: 現行の事前存在チェックは早期リターンとして残し（宛先がある再実行を無コストで終わらせるため）、最終確定は無条件の置換ではなく上書き不可の原子操作にする（Windows は置換なしの移動、POSIX はリンク＋削除の方式を候補とする）。事前チェックの後に宛先が作られて原子操作が失敗した場合は、そのジョブを失敗として数える（現行は上書きして成功扱いになる経路であり、差異は §5 に挙げる）。プラットフォーム側で実現できない場合は残存する競合範囲を明記する。
- 日時: atime／mtime は現行どおり置換前に付ける。Windows の作成日時も現行どおり置換前の一時ファイルへ付ける方式を維持する（リネームで保持される可能性が高いため。BUG-06）。Phase 0 のフィクスチャで保持されないことが判明した場合のみ、置換後の最終パスへ付ける方式へ変更する。

### 4.2 ベースライン計測（実装着手前に現行 Python 版で取る）

- コーパス（カテゴリごとに実ファイルを用意し、ファイル名と出所を記録する）:
  1. AI 生成 PNG（`parameters` 付き、Stealth 無し）― 主用途の代表
  2. Stealth 付き PNG（8bit／16bit 各1種以上）
  3. 16bit PNG（Stealth 無し）― H3 用
  4. JPEG（通常／CMYK／Orientation 付き／MPO／SOF 精度が 8 でないもの＝失敗確認用）
  5. GIF（単純な全面フレーム／最適化された部分フレーム＋disposal）― BUG-01 兼用
  6. APNG（`default_image` あり／なし／のみ、長尺、16bit APNG＝未対応の失敗確認用）
  7. 大きな静止画（4K 級）と小さな画像の大量バッチ（数百〜数千件）
  8. コピー主体の混合（AVIF／WebP／WebM 混在）
  9. ICC 付きの CMYK／L／LA 画像（D-CMS の合否材料）
- 計測項目: カテゴリごとの総時間と1件あたり中央値、ピークメモリ、出力バイト数、出力の画素等価性（§3.1 の合格基準で画素比較）とメタデータ読み戻し結果。BUG-01 の頻度判定はコーパスでは行わない（コーパスはカテゴリ別に意図的に選んだ標本ではないため）。利用者の実際の入力フォルダ群全体を母集団として無作為に数百件程度を抽出し、GIF の最適化有無を数える標本調査を別途行って記録する。数百件で最適化 GIF が0件でも、真の割合の上限は 1% 前後までしか絞れない（その規模でも数万件の運用では数百件の破損と両立する）ことを限界として記録する。
- 手順: 対象マシン（Windows、CPU／メモリ／ディスクを記録）で現行 Python 版を各3回実行し中央値を採る。各実行の開始前に出力フォルダと状態 DB を初期化する（初期化しないと2回目以降は全件再利用の時間、つまり SKIP の計測になる）。コールドは「OS のファイルキャッシュが冷えた状態での初回実行」、ウォームは「同じコーパスを読み終えた直後の実行」と定義し、区別して記録する。コールド状態の作り方（OS の再起動、またはキャッシュを追い出すのに十分な大容量ファイルの読み込み等）は手順に固定して記録する。ピークメモリは Python／Rust 共通の物差しとして、対象プロセスのピークワーキングセット（OS が提供する値）で測る。5% 基準のような小さい差の判定は、中央値のばらつきが基準を下回るまで実行回数を増やして行う。計測スクリプトと生ログは設計書と同じ場所に残す。
- 計測環境の記録には版情報を必須とする: Python／Pillow／Pillow 同梱 libwebp の版（Rust 側の計測では D-ENC で確定したエンコーダの版。案A ならクレートが束ねる libwebp の版、案D 採用時は `zenwebp` の版も含める）。版差と実装差を分離できない計測はやり直す。
- エンコーダ比較（案D の `zenwebp`）: Phase 0 でコーパス 1・2・7 の部分集合を使い、現行（libwebp）と総時間・出力バイト数・画素等価性を比較する。採用条件は §3.3 案D に定めた条件（総時間 20% 以上短縮、出力バイト数増加 3% 以内、画素が §3.1 の許容基準内、ライセンス解消）のすべてを満たすこと。
- 判定基準（案。Phase 0 の完了条件として確定する）: 静止画バッチ（コーパス 1・7、対象マシンの全コアを使う並列実行時）の総時間で現行比 2 倍以上を目標、単一ファイルで現行より 5% を超えて遅くなるカテゴリを作らない、Stealth 負ケースの追加コストは変換本体の 10% 以内を目標とする。この原案の値を既定とし、Phase 0 で変更する場合は変更理由を本書に記録する（基準を決める側と使う側が同じ Phase 内で閉じるため、緩和には記録を必須とする）。緩和方向の変更は Phase 0 の完了条件としては扱わず、本書の改訂（再レビュー対象）として切り分ける。

### 4.3 Rust 版の計測

- 計測は Phase 1（骨格時点の参考計測）、Phase 3（Stealth 負ケースの本計測）、Phase 5（本計測）で行い、同じコーパス・同じ手順でベースラインと比較して結果を記録する。失敗確認専用のカテゴリ（16bit APNG、MPO、SOF 精度が 8 でない JPEG 等）は全 Phase で速度比較の母集団から除外し、失敗の確認のみに使う（失敗によって判定基準を通過する形にしない）。Phase 5 の「全カテゴリ」は計測対象の全カテゴリを指す。計測範囲は Phase ごとに実装済みの範囲に限る: Phase 1 はコピーと静止画（コーパス 1・4・7・8。ただしコーパス 1 はメタデータ引き継ぎと Stealth を除く静止画変換分のみ、コーパス 4 は通常 JPEG のみ＝Orientation／CMYK は Phase 2 以降の範囲とし、MPO／SOF 精度違いは失敗確認のみで計測対象外とする）、Phase 3 は Stealth 対象（コーパス 2・3）に加えて負ケース確認としてコーパス 1 を再計測する（Stealth 実装後の追加コストを §4.2 の判定基準と照らすため）、Phase 5 は全カテゴリ。エンコーダ設定（quality／method／thread_level とジョブ並列度）の掃引は Phase 5 で行い、結果を本書に追記する。既定値は §7 項目1 で確定済みであり、掃引結果は見直しの提案として記録するに留める。変更する場合は利用者の再決定と §7 の改訂を経て、ゴールデン文字列の再固定を伴う（§3.7）。

## 7. 決定事項（旧・未決事項。2026-11-27 に利用者が決定）

1. lossless／method／exact は設定項目として追加する（決定済み。BUG-02／SPEC-01）。省略可能な新項目として `config.ini` の互換を保つ形に限る。既定値は現行挙動に合わせる（lossless は無効、method は現行の実効値＝静止画 4／アニメーション 0、exact は無効＝Pillow の既定どおり）。既定値の正本はコード内定数とし、同梱 config.ini テンプレはその複写とする（両者の一致をテストで確認する）。新項目の値域と検証規則: method は 0〜6（libwebp の範囲）、lossless／exact は真偽値、並列度は正の整数（未指定＝自動）。範囲外の値は現行の設定エラーと同じ扱いとし、起動時にエラーで終了する（終了コード 2。値域外を素通しして全件エンコード失敗に見える形にはしない）。キー名は、lossless／method／exact は既存の `[webp]` セクション、並列度は既存の `[output]` セクションの `parallel_jobs` とする（セクションは新設しない。新キーは検証の許可リストへ追加し、省略意味論はキー単位＝キーが無ければ既定値を使う）。キー名と値域検証は全項目分を Phase 1 で固定する（並列度は値の検証のみ Phase 1 で行い、プールへの反映は Phase 5）。真偽値の受理集合は現行項目と同じ（§1.3 の getboolean の受理集合）。並列度の明示値は CPU コア数でクランプし、クランプした場合は WARN を出す。exact は静止画にのみ適用する（Pillow のシーケンス保存には exact を渡す経路が無いため、アニメーションでは無効として扱う）。method／lossless は静止画・アニメーション双方に適用され、設定値がある場合はそれが優先する（§3.3 の method = 0 は未指定時の実効値である）。実装は Phase 1（静止画分）／Phase 4（アニメーション分）。
2. 並列度の設定項目を追加する（決定済み）。省略可能な新項目とし、既定値は自動（CPU コア数を上限とする）。キー名は `[output]` セクションの `parallel_jobs` とし、明示値は CPU コア数でクランプする（§7 項目1 の値域規則）。実装は Phase 5（キー名と値域検証の固定は Phase 1）。
3. Rust 版の置き場所は既存リポジトリ内の新フォルダとする（決定済み）。
4. 主対象 OS は Windows とする（決定済み。現行は `.bat` と pywin32 から Windows 主体）。POSIX のコード経路は残すが検証対象外とする。Phase 0 の前提とする。
5. `zenwebp` のライセンスは今は決めず、Phase 0 のベンチ結果を見て判断する（方針として決定済み。§3.3 案D）。ベンチが採用条件 (1)〜(3)（速度・サイズ・画素）を満たした場合にのみ判断が要り、その場合は Phase 0 終了時までに決定する。選択肢は商用ライセンスの取得、本プロジェクトのライセンス変更、採用しない、のいずれか。満たさなかった場合は判断不要として記録する。採用と決まった場合、静止画エンコーダの差し替えは Phase 0 の D-ENC 決着へ反映する（差し替えの実装自体は Phase 1 で行う）。
6. 16bit APNG は未対応とする（2026-11-27 決定）。現行 Python 版は変換できるため互換の後退だが受け入れる。検出したらジョブ単位の失敗として明示する。通常の 8bit APNG は対象のまま（§3.4）。

- [Python 公式ドキュメント `shutil`](https://docs.python.org/3/library/shutil.html): `copyfile()` がプラットフォーム固有の fast-copy を使う旨（PERF-07 の根拠）。

### 9.1 決定点の決着（要約）

D-ENC は `libwebp-sys` 0.14.4 の直接 FFI（同梱 libwebp 1.6.0＝Pillow 12/13 と同一版）、D-MUX は自前の RIFF 書き換え、D-EXIF は自前の最小 TIFF 実装、D-CMS は `lcms2` 6.3.0（sRGB はスレッドローカルに 1 回生成）、D-INI は自前パーサ、D-PAR は優先度付き自前プール、D-TIME は `filetime`＋`SetFileTime`、D-SIG はコンソール制御ハンドラ／シグナルでフラグのみ、D-LIMIT は画素数 178,956,970・辺 16,383・ERROR 文字列 4,096 バイト・停滞打ち切り 600 秒・掃除の最低経過時間 3,600 秒（倍率 10）、D-MEM は `sysinfo` の利用可能メモリ×0.5（256MiB〜8GiB）、D-LOCK は `Cargo.lock` の直接パース＋`--locked` 必須。根拠は Phase 0 記録 §2。

§7 項目5（`zenwebp` のライセンス）は「採用しない」で決着した。AGPL-3.0／商用ライセンスは MIT の本プロジェクトと両立せず、§3.3 案D の採用条件 (4) を満たせないため、条件 (1)〜(3) のベンチは判断不要として実施していない。

### 9.4 設計書からの主な差異

§3.3 の `webp` クレートは採用せず `libwebp-sys` 0.14.4 を直接使う（同梱 libwebp が 1.3.1 対 1.6.0 で画素が変わるため。`webp::WebPConfig::new()` も decoder ABI を渡す不具合を持つ）。ピクチャは Pillow と同じ ARGB（`use_argb = 1`）でインポートする。メタデータの格納は `img-parts` ではなく自前 RIFF 書き換えで行い、`Cargo.lock` の読み取りは `cargo metadata --offline` ではなく lock の直接パースによる。16bit グレースケールの 8bit 化は `min(v, 255)` クリップ、GIF の背景色は `(index, index, index, 255)`、UserComment は UTF-16BE とする。これらはいずれも Phase 0 の実測に基づく。UNC 出力では SQLite の WAL が SMB 上で共有メモリを作れないため、その場合だけロールバックジャーナルへフォールバックして WARN を出す（管理共有 `\\localhost\C$` で実測）。詳細と未達項目（実際の FFI パニックの注入、A1111/NovelAI の実画像、コールド I/O 計測）は実装記録 §5・§7 にある。
